## 一、结论先行

启动一个新项目时，不要让 Codex 一上来就写代码。先连接 GitHub 插件，用一段固定提示词强制它做一轮开源调研，输出技术选型、系统架构、MVP 范围和开发顺序，等确认后再进入实现。这样可以把第一轮 token 花在「找经过验证的方案、研究别人踩过的坑、做出技术取舍」上，而不是花在可能要重写的代码上。

可复制的提示词：

> 我要开发一个 XXX。暂时不要创建文件，也不要输出代码。先在 GitHub 调研同类开源项目，筛选出最有参考价值的方案。分析它们解决了什么问题、采用什么架构、依赖哪些技术、目前是否活跃，以及有哪些设计值得复用或避开。最后结合我的需求，给出技术选型、系统架构、MVP 范围和开发顺序。得到我的确认后，再进入实现阶段。

---

## 二、为什么「先调研后编码」能省 token

AI 编码最常见的浪费之一是：需求和技术方向还没确定时，就开始输出大量代码。一旦架构选型需要调整，这些代码往往要重写，前面的 token 就沉没了。

把第一轮改成调研，本质上是把 token 投入到「信息密度更高的阶段」：

| 投入方向 | 产出 | 是否容易重做 |
|---|---|---|
| 直接写代码 | 一堆可能用不上的文件 | 高，方向一变就重写 |
| 调研同类开源项目 | 选型依据、架构参考、踩坑清单 | 低，结论可复用到实现阶段 |

这与 [[文章/2026-07-15-004-Codex截图驱动的前端UI优化工作流]] 的「先完成结构再精修」是同一种思路：先稳定上游决策，再做下游实现。

## 三、四阶段工作流

### 阶段 1：调研（不创建文件、不输出代码）

提示词里的「暂时不要创建文件，也不要输出代码」是关键约束，强制 Codex 把这一轮花在阅读和分析上。

Codex 在这一阶段做三件事：

1. **找经过真实项目验证的方案**--在 GitHub 上搜索同类开源项目，而不是凭模型自身的记忆编造架构。
2. **研究别人已经踩过的坑**--从项目 README、issue、设计文档里识别哪些设计值得复用、哪些应该避开。
3. **根据需求做出技术取舍**--结合用户的 XXX 需求，而不是泛泛推荐「最流行」的方案。

调研维度建议覆盖：

- 解决了什么问题
- 采用什么架构
- 依赖哪些技术
- 目前是否活跃（维护状态、最近提交）
- 哪些设计值得复用或避开

### 阶段 2：选型输出

Codex 在调研后应给出四项明确结论：

- **技术选型**：用什么语言、框架、存储、依赖。
- **系统架构**：模块如何划分、数据如何流动。
- **MVP 范围**：第一版做什么、不做什么。
- **开发顺序**：先实现哪一块、后实现哪一块。

### 阶段 3：人工确认

这一步不可省略。LLM 筛选的开源项目和给出的选型仍需用户判断：

- 调研的项目是否真的活跃、可信；
- 选型是否匹配自己的团队能力和部署约束；
- MVP 范围是否合理，是否藏了隐藏复杂度。

确认前不进入实现，是这套流程省 token 的核心闸门。

### 阶段 4：实现

方向确定后，再让 Codex 开始写代码。此时架构、依赖、模块边界都已经收敛，实现阶段的返工概率显著降低。

## 四、与已有最佳实践的关系

这套提示词本质上是 [[文章/2026-07-11-019-Codex与Claude-Code使用最佳实践]] 中 Codex 推荐链路 `Project -> 独立 Task -> /plan -> /goal -> Subagent -> Worktree -> /review` 的前端延伸：在 `/plan` 之前，先做一轮 GitHub 源码级调研。

它也与 [[文章/2026-07-11-022-GitHub-Harness与Spec最佳实践项目运行机制]]、[[文章/2026-07-11-023-GitHub优秀Agent源码与框架拆解]] 的「先读源码再下结论」方法论同源--区别只是把调研动作前移到新项目的第零步，并由 Codex + GitHub 插件自动完成。

---

## 五、使用边界

- 「省 token」是经验性总结，未提供量化对比，不作为精确结论。
- GitHub 插件的能力与 Codex 的调研深度以当前产品为准，可能随版本变化；使用前应核对插件实际可访问的仓库范围。
- 调研结论不能替代亲自验证：LLM 筛选的项目仍需用户查看 README、issue 和活跃度，不能直接当作「已经过验证的方案」。
- 适用于新项目的方向探索阶段；已有明确架构的续开发不需要重复这轮调研。
- 提示词中的 XXX 需要替换为具体需求，描述越具体，调研越聚焦。
