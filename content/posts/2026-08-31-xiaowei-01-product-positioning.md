我曾把“模型回答得很完整”当成任务完成。一次 XLSX 任务让我改掉这个习惯：表格读对了吗，计算结果有没有写入 Artifact，用户批准的动作是否真的执行，下次打开还能不能找到结果，这些问题都不会自动包含在一段回复里。

小薇基于 DeepSeek Harness 开源底座。底座提供模型、工具、Session 和事件等可组合能力；产品化工作把它们接到桌面 Workspace、审批、后台 Job 和可打开产物上。

## 一份 XLSX 让我发现回答并没有交付

测试目录里放一份小型 XLSX，里面有日期、商品和金额列。我在 Session 里要求读取工作表、按商品汇总、生成一份结果文件，并说明原文件和结果文件的位置。这个任务足够小，能看清解析、计算和写文件三个动作。

聊天页返回了正确格式的摘要，我差点就结束验收。打开目录后才发现结果文件没有生成。模型完成的是语言输出，工具没有完成文件交付。于是我把验收对象从“回复文本”换成输入、计划、工具调用、审批、产物和恢复记录。

## 我先写完成判据，再设计交互

我现在会把任务写成五个字段：目标、输入文件、允许的写入位置、期望产物、完成判据。例如“读取 sales.xlsx 的 Sheet1，按商品汇总金额，结果写入 sales-summary.xlsx，保留原文件，完成后显示产物路径”。写清这些字段，Agent 才有机会选对工具，用户也知道该检查什么。

模型负责理解目标、生成计划和选择已注册 schema。Workspace 决定文件位置，Host provider 决定执行地点，工具策略决定能否读写，审批决定一次写入是否放行。联网或浏览器动作不会继承文件读取的批准。工具返回错误时，Session 要保留错误，而不是改写成一段乐观总结。

## 计划、工具和 Session 怎样接起来

短任务可以在当前 Session 内完成。需要多步处理或等待的任务，我会让 Agent 创建后台 Job；Job 保存状态、输入引用和输出引用，Workflow 负责按顺序执行步骤。后台执行不是页面外的黑箱，用户仍应能看到状态和最终产物。

桌面端同时维护本机和云端 Host。列表请求聚合两边，账号和钱包固定走云端，Session、Artifact 等资源依据资源 ID 中的位置回原 Host。XLSX 在本机 Workspace 时，读取和写入都发生在本机；导入云端 Workspace 后，才在云端副本上处理。不能仅凭同名资源或端口监听猜位置。

## 我按八步走完这次表格任务

1. 登录已认证账号，确认模型路由和钱包状态。
2. 创建本机 Workspace，添加测试目录和 sales.xlsx。
3. 创建 Session，先要求列出工作表和行数，再确认汇总口径。
4. 允许 Agent 读取 XLSX；读取结果要指出工作表、列名和样本范围。
5. 让 Agent 生成汇总计划，检查它引用的是当前文件而非凭空编造数据。
6. 写入 sales-summary.xlsx 前批准一次明确的文件操作。
7. 打开 Artifact，检查文件可下载、表格能打开、关键数值与源表一致。
8. 重启客户端，重新打开 Session，确认输入、工具结果和 Artifact 仍可见。

读取阶段看工具参数和实际文件；计划阶段看计算口径；写入阶段看审批事件和目标路径；交付阶段看产物是否真实存在。若回复写着“已生成”，但目录中没有文件，任务只能算失败。若文件存在但 Session 没有工具事件，后续也很难判断它来自哪次运行。

## 三种“成功”最后都没有交付

这通常说明模型完成了文本汇总，文件工具没有运行，或工具结果没有被产物面板接住。先查 Session 事件和工具返回，再查产物路径。不要让模型再次描述“已生成”来覆盖第一次失败。

附件接收、解析器读取和业务计算是不同步骤。文件类型或大小限制通过，不等于所有工作表都已读完。验收应保留实际工作表、范围和错误信息；超过限制时，应让用户缩小文件或拆分任务。

后台 Job 显示完成，只表示步骤状态结束。最终还要打开 Artifact，检查它是否绑定当前 Session 或 Workspace，重启后是否能恢复。对用户来说，可继续使用的文件比一条“完成”状态更重要。

## 我怎样证明结果真的存在

源码和打包验证只能证明实现和组合：`pnpm run typecheck`、`pnpm run test`、`pnpm run build` 属于这一层。真正交付前，我还会用安装后的客户端登录、创建 Workspace、执行 XLSX 读写并重启。这样能把“代码应该工作”和“用户真的拿到结果”分开。

至少要同时满足：源文件身份明确、工具读取有事件、写入经过审批、Artifact 能打开、Session 重启后可见。模型回复只是其中一项。如果用户只要求分析而不要求写文件，完成判据可以少一项，但必须在任务开始时写清。

好的任务提示不是写得更长，而是把文件、动作、权限和结果说清楚。Agent 可以帮助拆计划，但不能替用户决定数据范围，也不能用语言掩盖工具失败。对于企业使用，事件、审批和资源位置同样是产品结果。

输入是哪份文件？结果要落在哪里？用户准备批准哪一种副作用？这三个问题回答后，再选择本机或云端 Workspace、同步执行或后台 Job。完成后回到 Artifact 和重启恢复检查，而不是停在聊天页。

我会保存客户端版本、账号、Workspace 位置、Session、输入文件、工具参数、审批时间、Job 或 Workflow 状态、Artifact 路径和最终结果。失败时先保留错误原文，再重试。下一篇继续说明这些资源如何随账号切换，以及旧目录为什么必须显式认领。

任务结束后，我还会把输入文件和产物放在同一条记录里核对。若源表被修改，保留修改前后的文件名和时间；若只生成 Artifact，不把它误说成已写回 Workspace。对于后台 Job，记录开始、运行、失败或完成状态，避免只保存最后一条消息。这样下一次接手任务时，能知道应从原文件重跑，还是继续检查已有产物。

这次实录也改变了我对工具数量的看法。工具越多，计划越容易偏离目标。先把 XLSX 读取、计算、写入和产物展示四步跑通，再考虑搜索、浏览器或 Skill，验证成本更低，也更容易判断到底是哪一个 provider 失败。

这次任务还让我重新看待“自动化”。Job 和 Workflow 不是把责任交给后台，而是把每个步骤的状态留下来。输入文件、工具参数和输出引用都应能回看，失败时可以从具体步骤重试。用户批准一次写入，不代表后续所有写入都自动获得批准；权限要跟着动作走。

如果产物需要交给别人，我会再次打开文件，确认格式、名称和内容，而不是直接转发 Agent 的总结。对 XLSX 来说，结果可打开、数字可复算、源文件未被意外覆盖，才是可交付的最低要求。
