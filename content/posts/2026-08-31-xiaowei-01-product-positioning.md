我曾经把模型输出得很流畅，当作任务做完了。一次 XLSX 分析让我改了判断：用户还要知道读的是哪份工作簿、结果文件在哪里、失败发生在哪一步、下次能不能继续。小薇的产品定位从“对话体验”转到“任务交付”。

小薇基于 DeepSeek Harness 开源底座。模型、工具、Session 和事件由底座提供可替换能力；我负责把它们接成桌面和云端都能解释的产品路径。

## 背景：一次回答为什么不够
### 用一份小型 XLSX 验证

本文适合第一次设计 Agent 任务的人、产品验收人员和需要配置本机 Workspace 的开发者。准备一个已认证账号、一个测试目录和一份小型 XLSX。源码验证在仓库根目录执行。

“有文字返回”与“有结果可用”应分开记录。前者只涉及模型请求，后者还要求工具、权限、产物和 Session 状态都能解释。

聊天页能证明模型收到输入并返回文本，不能证明文件已经生成，也不能证明外部动作经过授权。对“整理资料”“分析表格”“更新目录”这类任务，我需要检查输入、工具、产物和历史。

小薇的本机 preset 包含文件、Shell、文档、表格、搜索、后台任务和工作流能力。每项能力都有 schema、作用域和执行位置。模型只是选择已注册工具，不能自行决定路径或账号。

## 目标与非目标：交付结果，不承诺模型万能
任务输入包括文字、Session 上下文、Workspace 文件和有界附件，输出则包括回复、工具结果、审批事件和可打开的产物。中间的输入、上下文、工具调用、审批、执行和结果都要能追踪，失败时还要留下明确错误与资源所在 Host。

账号 principal、Host、Session owner 和审批决定权限。这里不承诺模型结论永远正确，也不允许模型绕过批准执行外部副作用。联网网页只是外部数据，浏览器交互仍需独立授权和验收。

## 方案设计：让模型只做决策的一部分
### 对象关系

模型负责理解目标和选择 schema；工具 provider 负责执行；Session 日志记录已经发生的事件；Workspace 规定文件位置；产物提供交付入口。

### 配置与状态表

| 对象 | 输入 | 输出 | 权限来源 |
| --- | --- | --- | --- |
| Session | 用户消息与上下文 | 事件和回复 | owner 与环境 |
| Workspace | 源目录或副本 | 文件结果 | Host 策略 |
| 工具 | typed 参数 | typed 结果 | preset、scope、审批 |
| Skill | 用户内容 | 后续指令 | 安装批准与 Session 选择 |

DualHostRouter 同时维护本机和云端 Host。列表请求聚合两边结果，账号和钱包方法固定走云端，Session、Artifact 等请求按资源 ID 路由，不能把两个 Session 列表拼成没有位置标记的一份。

账号、路径、权限和审批由模型之外的组件决定。账号 principal 与 Session header 决定归属；工具注册表决定模型能看到哪些 schema；Host provider 决定工具在哪里运行；事件日志记录已经发生的事实。

本机和云端使用同一 RPC 信封，但执行世界不同。本机目录保持实时源目录，云端 Workspace 是账号私有副本。桌面端合并两边的事件流，并在资源 ID 上标记位置；后续读取、审批和取消都沿原位置返回对应 Host。

## 详细设计：从 XLSX 到 HTML 产物
### 第一次 E2E 操作

1. 登录并确认账号，以及目标 Workspace 位于本机还是云端。
2. 在本机 Workspace 放入测试 XLSX。
3. 创建 Session，请模型读取工作簿并调用 `sheet_analyze`。
4. 等待工具结果和审批提示，不要重复提交同一动作。
5. 打开生成的 HTML，核对来源、结果和 Session 事件。
6. 重启客户端，确认同一产物仍可访问。

### 安装 Skill 的输入输出

`skill_install` 输入是经用户确认的 Skill 内容和说明，不接受路径、账号或归属字段。输出是安装结果和后续发现状态。设备目录显示“已安装”，不代表当前 Session 已经加载；要在下一次请求中验证查找与调用。

文件不存在、解析超限、工具被拒绝、审批取消和 Host 不可用应保留不同错误。不要把所有失败改写成“模型暂时繁忙”，否则用户无法选择正确的恢复动作。

以表格分析为例，用户在当前 Session 上传或选择工作簿，`sheet_analyze` 读取有界数据，随后在本机账号专属 DSH_HOME 写入 HTML 产物；云端附件和云端结果留在云端。回复中应给出结果入口，而不是只贴一段摘要。

## QA 与上线验收：按用户可见结果验收
### 四层验证

源码层运行 `pnpm run typecheck`、`pnpm run test`、`pnpm run build`。打包层确认 `local-runtime` 和 IPC 文件存在。安装态层使用真实 Electron、账号、文件和重启。生产层检查下载文件与版本清单。

### 验证清单

- [ ] 输入文件属于当前 Workspace。
- [ ] 模型请求只包含用户有意加入的内容。
- [ ] 工具 schema、scope 和审批状态可见。
- [ ] 产物有明确路径并能重新打开。
- [ ] Session 重启后可恢复。
- [ ] `implemented`、`approved`、`observed` 分开记录。

账号隔离、认证闸门、本机文档分析和流连续性规格是 `implemented`。浏览器、Web 搜索路由和联邦工具有 `approved` 项。规格状态不能替代安装态验证。

验收要看产物是否存在、Session 重启后是否恢复、审批拒绝是否生效、断线后是否继续。单元测试说明代码行为，不能证明安装包中的 RPC、IPC 和 Host 连接真的走通。

## 踩坑：工具成功也可能没有交付
### 故障排查表

| 症状 | 检查顺序 | 处理 |
| --- | --- | --- |
| 只有文本没有文件 | 工具结果、产物路径 | 重新检查写入和展示链路 |
| Skill 出现在设置但模型找不到 | 当前 Session 能力选择 | 新建或恢复正确 Session |
| Host 断开 | pong、Host API、Session | 重开订阅，勿立即清理数据 |
| 浏览器结果影响判断 | 页面来源与授权 | 将页面当不受信任输入 |

0.3.40 反馈中出现过界面可用但服务缺失。排查时应核对 bundle、profile、安装包和真实调用，不能只看 `/health` 或开发进程。

### 误操作回避

不要连续重试会修改远端状态的工具；不要用 `dsh-ops` 的部署成功代替客户端验收；不要在结果未核对前刷新 Session，避免丢失现场。

第一个坑是只看模型文本。一次工具调用返回成功，但结果没有进入用户能打开的产物位置，任务仍然没有交付。第二个坑是把安装清单当作 Session 能力。设置页显示 Skill，只说明设备安装状态，不说明当前 Agent 已加载。

第三个坑是把断线当成 Workspace 损坏。桌面端的 mux 和 host 下行链路有独立心跳；缺少 pong 会重开连接并重新拉取会话，单纯没有应用事件不应直接标记工作区断开。

## 认知迭代：产品价值落在可接手的结果
### 最佳实践

先声明输入、环境和权限，再开始模型请求。工具完成后马上确认产物，重启后再确认可恢复。一个任务是否成功，应由用户能否继续处理结果来判断。

本机模式仍走账号模型路由和钱包；云端副本不自动同步本机目录；已安装 Skill 不等于当前 Session 已加载；外部浏览器动作需要单独授权。

`implemented` 表示已存在对应实现证据，`approved` 表示方案获批或待验收，`observed` 只说明特定版本或客户端观察到的结果。三者要在文档和发布报告中使用不同措辞。

## 日常使用与参考命令
每次任务记录账号、环境、Workspace、Session、输入文件、调用工具、审批、产物和错误。记录这些字段比保存一段完整聊天更容易定位归属和恢复问题。

仓库根目录可运行 `pnpm run typecheck`、`pnpm run test` 和 `pnpm run build`；博客目录运行 `node .agents/skills/blog-article-publisher/scripts/validate-post.mjs content/posts/2026-08-31-xiaowei-01-product-positioning.md`。命令只证明各自层级。

先用本机小文件验证结果，再尝试云端副本和需要批准的动作。不要用未完成规格的描述规划生产流程。

认证闸门、账号工作区隔离、本机文档分析、下行流连续性和本地 Skill 目录规格已有 `implemented` 记录；浏览器集成、账号 Web 搜索路由和联邦工具仍含 `approved` 项。它们是规格状态，不能推导出所有安装包都已发布。

任务模板至少包含目标、输入范围、禁止操作、输出格式、产物位置和完成判定。用户先提交模板，Agent 再补充计划；计划中的每一步对应一个工具或人工决定。计划不是权限，工具仍按 preset、scope 和审批执行。

短任务可以在当前 Session 直接执行。耗时工作先创建后台 Job，用户用任务页查看状态、收集结果或停止任务；停止只表示后续工作不再继续，不保证已经发生的外部副作用撤销。重复步骤较多时使用 Workflow，把输入、工具和失败分支写成可复用流程，但每次运行仍记录自己的 Session 和产物。

交付时打开产物，核对来源和生成时间，再把 Session 标识交给接手人。若只有模型文字、没有可打开结果，标记为未完成；若结果存在但账号或环境不明，先停止分享，回到归属检查。
