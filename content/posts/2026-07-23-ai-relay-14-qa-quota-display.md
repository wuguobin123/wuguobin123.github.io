## 一个奇怪的现象

部署完 codex2api 后，你打开 Codex CLI 试一下：

```
$ codex

> Hi
⚠️  Your weekly quota is exhausted. Upgrade to Pro for more.
```

gpt-5.6-sol 调不通了。

但你切到 CC Switch 配的 new-api → codex2api 渠道：

```
模型: gpt-5.6-sol
消息: hi
```

**通了**。

是不是很困惑？为什么 CLI 明明说"用光了"，代理又能用了？这篇文章把这件事彻底讲清楚。

## 一、一句话答案

> **codex CLI 显示的"额度用光"是 advisory（提示性），不是 enforcement（强制限制）。CLI 自己检查自己的额度提示，然后主动不发送请求。codex2api 不复制这个客户端检查，直接把请求发给后端——后端其实还能服务。**

更简单地说：

> **CLI 是"客户经理"——看到预算快没了就主动不让你用；codex2api 是"代购"——你说要就用，预算的事它不管。**

## 二、两个完全不同的概念

很多人混淆这两个术语，搞清楚后问题就清楚了：

```
Advisory（提示性）                       Enforcement（强制限制）
═══════════════════════                  ═══════════════════════
特点：                                   特点：
  - 不阻止请求                            - 真的不让请求到达
  - 客户端显示用"提示"                     - 后端返回 429 / 403
  - 自己判断                                - 服务端判断
  
在哪里：                                 在哪里：
  - codex CLI 内部                         - chatgpt.com 后端
  
例：                                     例：
  Codex CLI 看到 7d=100%                   后端 quota 真正耗尽
  显示"额度用光"                          返回 HTTP 429
  ❌ 不发送请求                            🔒 服务被中断
  UI 不让你用                              真的用不了
```

## 三、为什么 codex CLI 要做客户端检查

```
Codex CLI 的设计哲学：
  "宁可让用户少用一点，也不要让用户被后端 429 后报红错误"
  
  ↓ 实现方式：
  1. 启动时拉一次 wham/usage
  2. 每次请求前再查一次
  3. 如果显示配额紧张，就主动不调用
  4. 显示"请升级 Pro"提示
  
  优点：
    - 用户体验好（不会突然失败）
    - 鼓励升级付费
  
  缺点：
    - 显示数据可能被后端"放宽"
    - 用户实际能用的额度比显示的多
    - 切换代理后能"白嫖"差额
```

## 四、codex2api 不复制这个检查的好处

```
codex2api 的设计哲学：
  "我只是个转发器，配额的事让后端告诉我"
  
  ↓ 实现方式：
  1. 调度器只检查自己的健康分（5h >= 100% 才 banned）
  2. 不看 7d 是不是 100%
  3. 直接转发请求
  4. 如果后端真 429 了，再标 cooldown
```

具体调度逻辑（之前在 13 篇讲过的）：

```go
func computeHealthTier(usage5h, usage7d int) string {
    switch {
    case usage5h >= 100:    return "banned"   // ← 只有 5h 满了才禁
    case usage5h >= 80:     return "risky"    // ← 5h 接近满，谨慎
    case usage7d >= 80:     return "warm"     // ← 7d 满？无所谓
    default:                return "healthy"  // ← 默认健康
    }
}
```

**注意**：哪怕 7d=100%，只要 5h 还有空间，账号还是 warm，**调度器仍然会选它**。


## 六、为什么 OpenAI 让"显示"和"实际"有差距

这不是 bug，是 SaaS 系统的**标准做法**：

```
显示 vs 实际：SaaS 通行做法
═══════════════════════════

为什么？
  1. 防止误杀：用户接近限额时给"警告"，但不立刻断
     - 真实配额 = 显示 × 1.2 ~ 1.5
     - 客户体验更顺滑
  2. 鼓励升级：故意留 20% 余量让你焦虑"快没了"
     - 想用更多？升级 Pro / 加 credits
  3. 兼容客户端：不同客户端实现不同检查逻辑
     - 后端不强制 enforce
     - 客户端决定何时停（保守 or 激进）
  4. 历史原因：SLA 合同里承诺了"软限额"
     - 严格 enforce 100% 会触发 SLA 违约
     - 留缓冲是合规要求

实际比例（经验值，非官方）：
  ┌─────────────────────────────────────┐
  │ 显示 100% → 实际 130% 仍可调         │
  │ 显示 130% → 实际 150% 仍可调         │
  │ 显示 150% → 实际 180% 开始 429       │
  │ 显示 200% → 后端强制降级              │
  └─────────────────────────────────────┘
```

## 七、codex2api 实际能"白嫖"多少

```
理论最大差额：
═══════════════

  Codex CLI 显示 7d = 100% 时：
    - CLI: 完全不可用
    - codex2api: 还能继续用 30%-50% 的隐藏配额
    
  折算到月：
    - Plus 订阅原本 7d 大约 100 条 GPT-5 类调用
    - 通过 codex2api，可能多调 30-50 条
    - 月增 120-200 条（30%-50% 增量）
    
  折算到钱：
    - 多调 150 条/月 × 平均 1000 tokens/条
    - 等效节省 ≈ $1.5/月（按 API 按量算）
    - 不算大钱，但等于 7.5% 的 Plus 订阅费
```

**注意**：这个差额主要价值在**"重要时刻不被卡住"**——比如你深夜 debug 想跑一个任务，CLI 满了你睡不了，codex2api 让你继续。

## 八、调度器更精细的行为

如果你的账号池有多个账号，codex2api 的调度会利用这个差额**最大化池子整体利用率**：

```
多账号场景：

  账号 A: 7d 显示 100%（CLI 显示用光）
  账号 B: 7d 显示 80%
  账号 C: 7d 显示 50%

  你请求 gpt-5.6-sol
  
  调度器:
    1. 账号 A: 5h 健康 → 标 warm → 仍可选
    2. 账号 B: 5h 健康 → warm → 备选
    3. 账号 C: 5h 健康 → healthy → 优先
    
  选 C（healthy 优先）
  C 失败后才选 B
  B 失败后才选 A
  
  效果：把"健康"账号的额度留给真正的硬性场景
       "warm" 账号尽量榨干
```

## 九、什么时候这个机制会失败

不是所有情况都能"白嫖"，下面这些场景会真 429：

```
场景 1: 实际配额真的耗尽
━━━━━━━━━━━━━━━━━━━━━━━━
  5h = 100%（实际）
  7d = 200%（实际）
  → 后端硬性 429
  → codex2api 标记 cooldown 4h

场景 2: 高并发瞬时限速
━━━━━━━━━━━━━━━━━━━━━━
  你 1 秒发了 20 个 gpt-5.6-sol
  → 后端即使有 30% 余量也抗不住
  → 返回 429 + Retry-After
  → codex2api 短 cooldown

场景 3: 账号被封
━━━━━━━━━━━━━━
  OAuth refresh_token 失效
  → 账号整体不可用
  → codex2api 标记 error，跳过
```

## 十、给运营者的 3 条具体建议

### 1. 监控脚本要看真实余额，不是显示余额

```bash
# 不要这样监控（显示 100% 就慌）
DISPLAY=$(curl wham/usage | jq '.rate_limit.primary.used_percent')
if [ "$DISPLAY" -ge 100 ]; then
    echo "⚠️ 7d 显示满了，禁用账号"
fi

# 应该这样（wham 失败才慌）
RESP=$(curl wham/usage)
if [ $? -ne 0 ] || [ "$RESP" = "401" ]; then
    echo "⚠️ 账号真的不可用了"
    sqlite3 codex2api.db "UPDATE accounts SET status='error' WHERE id=..."
fi
```

### 2. 把"warm" 账号留到压轴用

在 new-api 渠道配置里，给 warm 账号留最低优先级：

```sql
-- 7d 100% 但 5h 还有的账号 → 兜底
UPDATE channels SET priority = 10, weight = 5 
WHERE id IN (SELECT channel_id FROM accounts WHERE health_tier='warm');

-- 真正健康的账号 → 主用
UPDATE channels SET priority = 80, weight = 100 
WHERE id IN (SELECT channel_id FROM accounts WHERE health_tier='healthy');
```

### 3. 不主动告诉用户"显示额度用光"

如果你的中转站有用户面板，**别显示"7d 100%"这种 advisory 数字**——它会让用户误以为服务挂了。改成显示：

```
✅ Codex 后端可用
最近 5h 真实余额: ~30%（估算）
最近 7d 真实余额: ~70%（估算）
```

## 十一、回到最初的问题

> **"Codex CLI 显示 7d 用光，gpt-5.6-sol 用不了。但通过代理又能用。"**

完整回答：

```
1. Codex CLI 显示的是 advisory（wham/usage 拉到的展示数字）
2. CLI 自己做了客户端检查，看到 7d=100% 就主动拒绝发送
3. codex2api 不复制这个客户端检查
4. 真实情况：OpenAI 后端配额还剩 ~30% 隐藏余量
5. codex2api 把请求直接发给后端，后端正常服务
6. 结果：CLI 用不了的模型，codex2api 还能用

本质：
  这是 SaaS 系统的"软限额"标准做法
  + codex2api 利用了"显示 vs 实际"的差
  + 这不是 bug，是 feature
```

## 十二、会不会被 OpenAI 风控

合理的担心。答案是：

```
短期（个人使用）：
  ✅ 不会。即使多用 30% 也不触发风控。
     OpenAI 对付费用户是宽容的。
     
中期（团队共享）：
  ⚠️ 边际风险。如果多个账号都这么搞，
     行为模式可能跟"自然用户"偏差大。
     建议：保持各账号使用率 < 80% 显示值，
     给自己留缓冲。
     
长期（商业转售）：
  🔴 高风险。多个 Plus 账号叠加利用差额，
     是明显的滥用模式。被检测到后批量封号概率高。
```

**建议**：自用和团队共享完全 OK；对外商业转售别碰这个差额，那是找封。

## 小结

这是 codex2api 这种代理的"隐藏价值"之一——通过绕开客户端的保守检查，让用户能用满 Plus 订阅的真实容量。

但这是个 **soft optimization**，不是 magic：

- ✅ 可以多调 30%-50%
- ✅ 不需要任何额外付费
- ⚠️ 不能违反账号使用规范
- ⚠️ 商业场景风险高

记住：**advisory ≠ enforcement**。这是理解所有 SaaS 配额系统的核心认知。
