上一篇文章里，我复盘了如何在两天内完成「算一卦」微信小程序。从结果看，它包含完整的问事流程、云函数、大模型解读、历史记录、隐私设置和分享能力。

这条流水线还有一个容易被忽略的前提：我不必一直坐在电脑前。任务在 Mac 上继续运行时，我可以从手机进入同一个 ChatGPT/Codex 任务，查看进度、补充约束、回答问题或处理确认。它没有缩短模型计算和工具执行的时间，却减少了“人离开电脑，任务就停住”的等待。

**手机不是新的开发机，而是正在运行的 AI Coding 会话的遥控器。** 具体连接方法、适用场景和远程桌面兜底方案，我整理在系列第 3 篇：[用手机远程控制 ChatGPT](/posts/2026-07-20-control-chatgpt-from-phone/)。

但如果只把速度归因于“AI 写代码很快”，就会漏掉这次实践里最重要的部分。

传统开发最耗时的地方，往往不是写某一个页面，而是灵感、需求、文档、设计、代码和测试之间不断重新解释。每换一个阶段，都要把脑子里的想法再翻译一次。其中一次交接不完整，后面就会用返工补回来。

这次真正起作用的，是一条连续的生产线：

**推文灵感 → Ask 模式讨论 → PRD → Stitch 原型 → WorkBuddy 代码框架 → Computer Use 真机验收。**

每一步的结果，都直接成为下一步的输入。

## 真正的提效，发生在六次交接里

如果用传统方式推进，一个模糊想法通常要先写成需求，再整理成 PRD；设计师重新理解 PRD 后制作原型，开发者再根据原型和文档重建页面，最后测试人员从运行结果中寻找遗漏。

这条链路的问题不是分工，而是信息在不同载体之间反复损耗。

一句”希望产品有东方韵味”，到了需求阶段要解释成用户感受，到了设计阶段要解释成色彩、字体和动效，到了开发阶段又要解释成具体组件、资源与样式。如果每个阶段只拿到一句话，所有人都会从自己的经验出发补全空白。

AI Coding 带来的效率，首先是让这些上下文可以连续保留。然后是每个阶段都留下可以被下一个工具继续读取的成果，而不是只留下一段聊天记录。

因此，这次流程并不是六个工具简单串联，而是六次信息交接被逐步结构化。

## 一条推文只负责点火，不负责定义产品

「算一卦」最初的灵感来自推特上的一条推文。

推文适合触发兴趣，却不是需求文档。它能让我意识到“这里也许有一个产品机会”，但不能回答用户是谁、为什么使用、流程是否成立、什么内容应该做、什么内容不能做。

过去遇到这种灵感，我很容易直接打开编辑器，先做一个首页或功能入口。这样很快就能看到东西，但最早写下的页面结构会变成一种路径依赖：后续即使发现产品逻辑有问题，也会因为代码已经存在而不愿意推倒。

这次我没有马上写代码，而是先保留灵感，再把它改写成几个需要验证的问题：

- 用户真正想解决的是“预测未来”，还是整理当下的困扰？
- 传统文化元素应该是产品结论，还是帮助用户进入状态的体验媒介？
- 什么内容适合分享，什么信息必须默认隐藏？
- 个体开发者能够完成的功能边界和正式上线边界分别在哪里？

灵感阶段的提效，不是更快地产出页面，而是更早发现不值得做或需要改写的部分。

## Ask 模式先挑战需求，再帮助收束

第二阶段，我使用 ChatGPT 5.6 的 Ask 模式反复讨论需求可行性。

这里的重点不是让模型替我决定产品，而是把它当成一个持续追问的产品搭档。每当我提出一个功能，它都需要继续追问：这个功能解决什么问题？与前一步有什么关系？用户为什么愿意继续？如果去掉它，主流程是否仍然成立？

项目早期叫「玄鉴」，首页同时放着易经、塔罗、MBTI 和星座四个入口。它看起来能力丰富，但讨论后逐渐暴露出一个问题：这更像一张工具菜单，而不是一条完整的用户任务。

用户先描述自己的现状，接着回答关联不强的问题，再去抽一张卡，最后等待综合报告。每一步单独看都能解释，连在一起却缺少自然的因果关系。

经过多轮讨论，产品被重新收束为：

**先说自己的问题，再回答针对性追问，然后静心求一支签，最后获得结合问题与回答的解读。**

易经、塔罗、MBTI 和星座没有被简单删除，而是退出首页竞争，成为文化背景、参考资料或后续能力。主流程只保留用户此刻需要完成的下一步。

Ask 模式在这里节省的，是“做出来之后才发现需求不顺”的返工时间。

## PRD 不是重新写，而是把讨论固化

需求讨论稳定后，我没有重新打开一个空白文档回忆结论，而是让 ChatGPT 5.6 直接基于前面的完整上下文生成第一版 PRD。

因为上游讨论已经覆盖了产品定位、目标用户、主流程、风险边界、分享规则和上线约束，PRD 生成不再是一次从零开始的写作，而是把已经形成的决策固化为可执行结构。

这份文档继续补全了页面目标、交互规则、数据边界、云函数职责、失败状态和验收条件。后续即使产品方向调整，也可以明确判断应该修改哪一层，而不是把所有问题都留给页面代码处理。

其中一条规则后来反复用到：

> 原型是界面基准，PRD 是行为和边界基准。

这句话把两个经常混在一起的问题分开了。页面长什么样，以原型为准；数据怎么流转、模型能做什么、失败如何处理，以 PRD 为准。

PRD 阶段的提效不是”模型几分钟写完一份长文档”，而是讨论结果没有在进入设计和开发前丢失。

## Stitch 把抽象需求变成可验证界面

第四阶段，我把 PRD 直接交给 Google Stitch 生成原型，并通过多轮对话持续调整页面。

Google 对 Stitch 的官方介绍是：它可以根据自然语言、图片或线框图生成 UI，并提供对应的前端代码，让设计可以继续迭代并进入开发流程。[Google Developers Blog](https://developers.googleblog.com/en/stitch-a-new-way-to-design-uis/)

这与本项目的需求很匹配。PRD 描述的是产品逻辑，但“东方韵味”“安静的仪式感”“报告需要可信而不是神秘”仍然需要被转成看得见的界面。

Stitch 的第一版并不是最终答案。页面会出现中英文混用、重复稿、缺少加载状态、导航不一致等问题。通过反复调整，最终导出的压缩包包含 12 组页面截图与对应 HTML，以及一份 `DESIGN.md` 设计规范。

这些成果有两种价值：

- 截图让人可以快速判断视觉方向是否正确；
- HTML 和设计规范让后续编码工具可以读取布局、层级、颜色与组件关系。

代码版本的原型并不等于生产代码，但它比一张静态图片多了一层机器可读的信息。开发阶段不再需要仅凭截图猜测间距、层级和组件结构。

## WorkBuddy 先铺开系统骨架，再补足实现深度

第五阶段，我把 PRD 和 Stitch 导出的原型代码一起交给 WorkBuddy，生成第一版微信小程序框架。

PRD 负责说明行为边界，原型代码负责说明视觉结构，两者一起输入后，WorkBuddy 可以同时建立页面、组件、数据结构和云函数，而不是先做一张首页，再等待下一条零散指令。

初版工程一次性铺开了主流程页面、协议页、公共组件、共享业务模块和云函数骨架，同时增加纯函数测试与 PRD 验收脚本。v1.0.0 阶段已经具备 11 个主流程页面、2 个协议页、13 个组件、22 个云函数入口、7 组核心测试和 172 项自动检查。

这些数字不代表初版已经可以直接上线。它们说明的是：AI 很适合先把系统的“宽度”搭起来，让页面、云端、数据和测试都有明确位置。

如果完全依靠逐页手写，我会在很长一段时间里只看到局部页面；框架先铺开之后，缺失状态、接口冲突和流程断点会更早暴露。

但这个阶段仍然只是“代码看起来完整”。微信能否编译、云函数是否真正部署、模型能否返回报告、手机上是否溢出，还需要进入真实环境验证。

## Computer Use 把代码完成推进到产品完成

最后阶段，我使用 ChatGPT 5.6 的 Computer Use 插件操作微信开发者工具，完成编译、联调、真机预览和交互验收。

这一步是整个流程里最容易被忽略、却最关键的提效环节。

只阅读代码，模型可能认为页面已经完成；真正打开微信开发者工具后，问题会变得非常具体：TabBar 图标格式不被支持、WXSS 选择器无法编译、云环境与 AppID 没有关联、模型调用超时、导航被重复触发、报告页渲染两次、底部弹窗在某些手机上溢出。

Computer Use 让 AI 不只看源文件，还能看到工具实际显示了什么。每轮修改都可以形成一个完整闭环：

1. 在开发者工具中编译并走一遍真实流程；
2. 读取报错、页面状态或真机截图；
3. 回到代码定位相关页面、样式与云函数；
4. 修改后重新编译；
5. 再次确认问题是否消失。

这一阶段也把视觉验收纳入同一条链路。首页与设计稿差距较大时，我直接提供真机截图，让模型继续调整印章位置、箭头居中、首屏高度和底部安全区，而不是只根据代码推测最终效果。

![经过真机验收后的「算一卦」首页](../../images/2026-07-19-suanyigua/01-home.png)

报告流程同样经过真实云函数与模型调用验证，而不是停在模拟数据或静态页面。

![真实模型生成的解签报告](../../images/2026-07-19-suanyigua/07-report-top.png)

Computer Use 节省的不是一次点击，而是把“发现问题—修改代码—重新验证”压缩在同一个持续上下文中。

## 这套流程为什么能够提效

回头看，这条链路里有四个真正有效的加速点。

同一份上下文持续向后流动。需求讨论中的取舍进入 PRD，PRD 进入原型，原型代码与 PRD 一起进入工程，运行错误和截图再回到代码上下文。很多信息不需要反复口头转述。

每个阶段都交付可继续加工的成果。Ask 模式留下明确决策，PRD 留下规则和验收条件，Stitch 留下截图、HTML 与设计规范，WorkBuddy 留下可运行框架，Computer Use 留下真实环境验证结果。

先建立完整闭环，再优化局部质量。初版优先让产品、前端、云端、模型和测试都有位置。主流程跑通之后，再集中优化首页、报告、弹窗、导航和动效，避免在错误方向上过早精雕细琢。

人负责判断，AI 负责加速执行。是否删除四个入口、追问是否真的相关、趣味与可信如何取舍，这些产品判断不能外包。目标清楚之后，文档整理、原型探索、跨文件修改和重复验证才适合交给 AI。

这也是我对 AI Coding 效率最直接的理解：它不是把某一个环节压缩到零，而是把六个环节之间的等待、转述和返工降到更低。

从一条推文到一款完整小程序，中间仍然需要大量判断和修改。变化在于，每一次判断都可以迅速变成下一个可验证的产品状态。

这比“一句话生成一个 App”更接近这次实践的真实过程，也更像一套可以复用到下一个产品的工作方法。
