我一开始把 Workbuddy 的核心理解得很简单：用户给出目标，Agent 读文件、调用工具，最后把结果交回来。真正把这件事做成小薇后，难点不在聊天框，而在“结果到底属于谁、在哪执行、能不能恢复”。这篇记录我如何从一个可对话的底座，取舍出一条可执行的产品主线。

小薇基于 DeepSeek Harness 开源底座做产品化、集成和交付。插件、模型适配器、工具注册、事件和 Session 等基础能力来自底座；账号、双 Host、桌面交互、数据归属和发布验收，是产品化工作要补齐的部分。

## 从 Workbuddy 迁移时，我先放下了聊天中心

Workbuddy 的价值在于让 Agent 真正碰到文件和工具。用户不是只想看一段漂亮文字，而是希望目录被整理、表格被分析、结果留得住。迁移到小薇时，这个起点没有变，但桌面客户端增加了账号、权限、Host 和安装态问题。

我没有从零造一套 Agent 框架。DeepSeek Harness 已经提供了可组合的插件机制和事件记录，我把精力放在产品路径：本机和云端如何同时存在，工具如何按位置执行，用户如何批准写入，重启后如何继续找到原来的 Session。

## 我先把“小薇要交付什么”想清楚

小薇要交付的不是一句回答，而是一项可以核对的任务结果。输入可以是文字、Workspace 文件或附件，输出可以是回复、工具结果、事件和产物。账号、Workspace、Session 所在 Host 和审批记录共同决定这次执行能不能发生。

它不承诺模型结论天然正确，也不把本机 Host 写成离线模型。本机推理仍走认证账号的模型路由并消耗钱包。云端 Workspace 是账号副本，不会自动追踪本机目录。浏览器、联网和外部写入也不会因为普通读文件获得同样权限。

## 两个 Host 怎样共同承接一次任务

桌面端同时维护本机 `xiaowei-local` Host 和云端 Host。`DualHostRouter` 负责把它们放进一个用户入口：列表请求聚合两边结果，账号和钱包方法固定走云端，Session、Artifact 等资源请求按资源 ID 中的位置路由回原 Host。两个 Host 是并存的。

本机 Workspace 保存用户选择的规范路径，云端 Workspace 则是明确导入后的账号私有副本。资源位置必须进入路由信息，不能看到同名 Workspace 就猜测归属。Host 监听端口也不是就绪信号，至少要等 `workspace.list` 能按账号返回资源。

### 产品能力地图

我把已经接入产品主线的能力放进一张表。它不是功能名录，而是回答五个实际问题：用户从哪里进入、事情在哪里执行、谁有权批准、最后留下什么、目前能做到哪一步。

| 能力域 | 用户入口 | 本机或云端归属 | 权限与审批 | 交付物 | 目前的实际表现 |
| --- | --- | --- | --- | --- | --- |
| 账号与商业 | 登录、注册、钱包、模型设置 | 账号和钱包在云端 | 账号认证、额度约束 | 账号状态、模型请求 | 登录后才能进入任务主线；商业规则由云端控制 |
| Workspace / Session | 列表、创建、Session 页面 | Workspace 可本机或云端；Session 跟随 Workspace | owner、位置、Session 权限 | 目录引用、事件、历史 | 本机与云端资源可以同屏查看，但不会混写 |
| Agent 执行 | 对话、Plan、Todo、Goal、Job、Workflow、Subagent、上下文压缩 | 对应 Host | 工具调用、写入和副作用审批 | 回复、工具结果、任务状态 | 短任务留在 Session，长任务保留独立状态和恢复点 |
| 文件与 Shell | 文件浏览、读写、命令 | 本机 Workspace 的本机路径 | 路径和命令策略，写入需批准 | 文件变更、命令输出 | 直接操作选定目录，不会悄悄复制整棵目录 |
| 网络与浏览器 | 搜索、网页读取、浏览器 | 有相应能力的 Host | 网络和页面副作用单独授权 | 搜索结果、页面内容、操作结果 | 与文件权限分开，不能因为能读文件就自动操作网页 |
| 文档与产物 | PDF、DOCX、XLSX、PPTX、产物面板 | 本机附件在账号专属设备 `DSH_HOME`；云端附件在云端 | 类型、大小、分析动作受限 | 摘要、表格结果、可下载文件 | 可以分段读取 PDF；Office 文件仍受完整解析上限影响 |
| Skill 插件 | 安装、目录、Session 工具 | 账号或本机 preset | 来源、安装权、当前 Session 加载 | Skill 和工具结果 | 安装后仍要确认当前 Session 是否加载 |
| 知识检索 | 任务中的知识工具 | 跟随账号和 Provider | 租户与数据源隔离 | 检索片段 | 已留出替换接口，接入真实数据前仍需单独验证 |
| 桌面体验 | Electron 登录、流式消息、恢复 | main/preload/renderer 连接双 Host | IPC、RPC、认证闸门 | 可见状态和恢复资源 | 支持登录门禁、流式消息、断线恢复和更新 |
| 安全治理 | 切换账号、旧目录、审批 | 运行时按 `authority + user` 派生 | owner、认领决策、事件 | 隔离目录、审计记录 | 旧目录只能拒绝或明确认领，不会自动归给新账号 |

### 首次使用流程

我会准备一个已认证账号、一台可运行 Electron 的设备、一个不含敏感资料的测试目录，以及 `xiaowei-read-write.txt`。操作顺序如下：

1. 登录，确认当前账号、模型路由和钱包状态。
2. 创建位置为本机的 Workspace，选择测试目录。
3. 创建 Session，让 Agent 读取文本并生成摘要。
4. 在明确的审批提示出现后，批准一次写入，让它更新测试文件。
5. 打开回复、工具结果和产物，检查文件内容确实改变。
6. 退出并重启客户端，重新打开 Workspace 和 Session，核对事件、审批和产物仍属于同一账号。

读成功只证明读成功；写入还要看文件内容、权限和事件。看到一个模型回复，也不能代替这三项检查。

### 三类数据不要混用

本机目录是实时源，系统接收的是用户选定的规范路径，不会自动枚举和复制。云端 Workspace 只有在明确执行 `workspace.importDirectory` 后才产生账号私有副本，本机后续修改不会自动同步。附件是第三条路径：本机附件留在账号专属设备 `DSH_HOME`，云端附件留在云端存储，不能用本机路径推断云端实现。

账号本机运行时身份由 `authority + user` 派生。无 owner 的旧目录不自动分配：拒绝认领时使用干净目录且决策持久化；确认认领时复制到账号目录，保留旧源，并用 claim 标记阻止其他账号再次导入。

## 页面能开，为什么还不能算已就绪

### 三个容易误判的信号

页面能打开，只能证明 renderer 打开。端口在监听，只能证明某个进程存在。`/health` 返回成功，只能证明健康探针可达。真正的产品就绪要看账号、`workspace.list`、工具执行和 Session 恢复。

0.3.40 的历史观察就是例子：反馈按钮能点，但 Host 组合漏了 `message-feedback`，本机提示“反馈保存失败”。检查 `local-runtime/storages/message_feedback.json` 是否写入，比只看页面和 `/health` 更接近真实结果。

我会把源码、打包、安装态、生产四层分开。`pnpm run typecheck`、`pnpm run test`、`pnpm run build` 是源码和构建证据；安装真实客户端后登录、读写、审批、重启，才是安装态证据；版本文件、稳定别名、安装脚本和 `latest.json` 才属于生产下载证据。报告同时记录版本、账号、Workspace、Session、输入文件和实际观察。

先确认数据归属，再确认工具权限，再确认交付物位置，最后做重启恢复。这样看，聊天是入口，Session 是过程记录，Workspace 是执行位置，Artifact 是交付出口。四者缺一个，任务就可能只剩一段看似完整的回答。

第一次使用，我更愿意从小文件和本机 Workspace 开始。基础读写、审批和恢复走通后，再加入云端副本、浏览器、联网或 Skill。每加一项能力，都重新问一遍数据归谁、动作在哪里发生、结果留下了吗。这个顺序看起来保守，却是小薇从演示走向产品时最重要的一次思路变化。
