## 先把一个常见误会拆掉

「Agent」这个词被用烂了。

去 Notion 搜一下，你会发现它当下至少有四种含义：

- 营销页里把它当成「自动化的 Chatbot」
- 论文里把它当成「能调用工具的 LLM」
- 工程师眼里它是「循环 + 状态 + 工具的可执行系统」
- 公司愿景里它是「能自己规划、长期协作的 AI 同事」

差别非常大，后面三种根本不在一个难度等级上。

我自己的判断：**Agent 不等于更聪明的模型，它是一个系统工程。** 模型是发动机，但车还需要变速箱、轮胎、刹车、油门、仪表盘、ESP、司机。Harness 就是那一整套把发动机变成车的东西。

这篇就来拆这个车是怎么一步步搭起来的。

## 六个历史阶段

我习惯把 Agent 的演进分成六段。这不是按论文时间排，而是按「真实系统里需要解决的问题」排。

```
Chatbot → Tool Calling → AgentLoop → Runtime → Harness → 主动式 / Multi-Agent
```

### 1. Chatbot：语言交互入口

模型负责问答、总结、生成。外部系统完全不参与。

好处：产品简单、风险好控。坏处：访问不到实时数据，执行不了任何任务。

2022 年之前基本就停留在这。

### 2. Tool Calling：模型开始连接外部世界

搜索、数据库、代码执行、浏览器被封装成一个个工具，模型从「回答者」变成「选择用哪个工具的回答者」。

这一步很快暴露新问题：

- 参数拼错（调用搜索却没传 query）
- 工具幻觉（明明没有这个 API，模型硬说有）
- 错误循环（同一行错误反复修）
- 不知道怎么停（任务完成了还在调）

简单函数调用解决不了这些，于是走到第三阶段。

### 3. AgentLoop：形成执行循环

经典 ReAct 范式：

```
读上下文 → 决定下一步 → 调工具 → 拿到结果 → 更新状态 → 再决定下一步 → ...
```

这套循环让「多步任务」成为可能，但也带来上下文膨胀、成本失控、错误累积这些新毛病。

一个 30 步的任务，到第 20 步时上下文已经塞满了之前的失败日志，模型开始重复自己。

### 4. Runtime：把循环放进可恢复的执行环境

长任务需要 checkpoint、重试、幂等、超时、中断、人工介入。

LangGraph、Inngest、Trigger.dev 这些系统做的事情，本质上是把 AgentLoop 装进一个可以中断、恢复、并行、补偿的 orchestration runtime。

模型终于可以一次性跑几小时了。

### 5. Harness：全局控制与质量保证

光有 Runtime 还不够，因为模型还是会出错、还是会偏题、还是会做不该做的事。

Claude Code、Manus、OpenClaw 这些产品开始显式建模：

- 规则：什么能做、什么不能做
- Context：每次送入模型哪些信息
- 工具权限：哪个工具要审批、哪个工具直接放行
- 流程：先读规则、再建计划、边做边更新
- 并发：Planner/Worker/Judge 怎么分工
- 预算：单任务最多花多少 token、多少钱
- 验证：代码跑没跑？测试过没过？文件在不在？

这一层就是 Harness。

### 6. 主动式与 Multi-Agent

最后两个方向：

- **主动式 Agent**：持续观察环境，在合适时机主动发起任务（而不是等用户问）。例：监控到 GitHub issue 异常 → 自动分析 → 推送报告。
- **Multi-Agent**：Planner、Worker、Judge 多个角色分工。OpenAI Swarm、Anthropic Multi-Agent、AutoGen 都在做这个。

两个方向都放大了权限、隐私、责任和成本风险。

## 一个生产级 Agent 的七层结构

把上面六段抽出来，加上 Context 单独成层，下面是我自己用的拆解：

```
┌────────────────────────────────────┐
│ 7. Evaluation       │ 评测、回归、用户反馈 │
├────────────────────────────────────┤
│ 6. Control          │ 权限、预算、审批、终止 │
├────────────────────────────────────┤
│ 5. State            │ 进度、依赖、checkpoint │
├────────────────────────────────────┤
│ 4. Tool             │ API、Browser、Terminal、DB │
├────────────────────────────────────┤
│ 3. Memory           │ 跨任务长期记忆 │
├────────────────────────────────────┤
│ 2. Context          │ 本轮送入模型的信息 │
├────────────────────────────────────┤
│ 1. Model            │ 推理 + 规划 + 工具选择 │
└────────────────────────────────────┘
```

**最容易漏的就是 4-7 层。** 很多人写完大模型调用就以为做完了，结果：

- 没有 State，任务跑到一半崩溃就全废
- 没有 Control，Agent 误删生产数据库
- 没有 Evaluation，效果好坏全靠感觉

## Context、Memory 和 Subagent：三个最容易混淆的概念

### Context vs Memory

很多人混着用，我严格区分：

- **Context**：本轮模型能看见的信息。Context Window 限制的就是这个。
- **Memory**：跨任务、跨会话保存的信息。数据库 / 笔记 / 配置文件都属于这一层。

Memory 只有被正确召回并塞进 Context 才有用。所以 Memory 系统的设计核心问题就是：

- **记什么**：原话、摘要、向量化、还是结构化？
- **存多久**：永不过期、滑动窗口、还是按重要度衰减？
- **何时取**：每轮都取、显式查询、还是 trigger 触发？
- **由谁管理**：Agent 自己、还是外部程序？

召回太多会污染窗口，召回太少又会失去连续性。

### Subagent：不是「并行工具」

Subagent 同时承担三种作用：

1. **并行执行**：多个 Subagent 一起跑，节省时间
2. **专业分工**：一个查代码、一个查文档、一个查 Slack
3. **上下文隔离**：主 Agent 不必读所有原始工具结果，只接收结构化结论

但 Subagent 边界如果划不清，会制造重复劳动、状态冲突、责任真空。常见反模式：

- 主 Agent 和 Subagent 都去改同一个文件
- Subagent 之间各自为战，谁都不传最终结果
- Subagent 失败但主 Agent 误以为成功

## Harness 的三件事

我接触了十几个团队的 Agent 系统后，Harness 真正核心的活儿其实就是三件事：

### 1. 流程控制

让 Agent 先读规则、再建计划、边做边记录，关键节点请求确认。

不是为了「机械限制模型」，而是为了降低遗漏和虚假完成。

### 2. 并发控制

- Planner 拆解任务、声明依赖
- Worker 负责局部执行
- Judge 独立验证

共享状态要最小化，高风险写操作要唯一所有者。

### 3. 验证控制

- 代码运行、文件存在、权限合规 → 优先用代码检查
- 开放式质量（文案、设计、对话体验） → 用 LLM-as-Judge
- 兜底 → 人工复核

**LLM-as-Judge 不应该成为唯一证据。** 评测环境要只读或隔离，否则 Agent 学会「修改测试让自己通过」。

## 补偿面：Harness 不是越堆越好

这是我自己最深刻的认知之一。

Planner、记事本、Context Reset、复杂规则、强制审核——这些本质上都是**对当前模型缺陷的补偿**。

模型升级后，旧组件可能不再有用，反而会增加延迟和成本。

成熟团队会在每次模型升级后做一件事：

```
保留旧 Harness → 逐项拆除组件 → 跑回归 → 比较质量与成本
```

护城河不是 Harness 的厚度，而是**识别补偿面迁移的速度**。

## 关键认知

- Agent 的竞争已从模型比拼转向系统比拼。
- 全局控制权应属于 Harness，局部自由度留给模型。
- 可观测性回答「发生了什么」，评测回答「是否正确」。
- 验证优先用代码检查，LLM-as-Judge 兜底。
- Harness 是补偿面，要随模型迭代做减法。
- 长期壁垒更可能是任务轨迹、私域知识、Eval 和组织迭代能力，而不是固定工作流。

## 常见误区

- 把工具调用当成完整 Agent
- 用更多 Agent 掩盖任务边界不清
- 让生成者自我评价
- 只看成功 Demo，不看失败恢复
- 模型一升级就停止维护 Harness（其实应该反向瘦身）

## 观察指标

- 长任务完成率
- 失败恢复率
- 人工介入次数
- 权限违规率
- 单任务成本
- 真实业务替代程度
