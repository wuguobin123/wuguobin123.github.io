我在发布小薇时最容易问错一句话：“包能打开吗？”0.3.40 给了一个更具体的答案：界面能开，服务却可能缺失；部署脚本能跑，目标服务却可能不是生产服务；清单能访问，latest.json 也可能已经指向一个没有准备好的版本。于是我把发布工作改成从证据到顺序的一条流水线。

小薇基于 DeepSeek Harness 开源底座做产品化和交付。底座负责插件、事件和运行时扩展，发布工作还要负责桌面组合、服务端、安装器、COS 对象和回退入口。

## 0.3.40 让我停止相信单一信号

0.3.40 中，反馈按钮可以点击，界面也能显示状态，但本机提示“反馈保存失败”。追到 Host 组合后，发现设备运行时漏挂 message-feedback 服务。这个观察说明页面和 RPC 路由存在，不代表本地持久化能力已经装配。

一次部署误用了面向 dsh-ops.service 的脚本，而生产实际运行的是 dsh-xiaowei.service。脚本成功退出并不能证明目标服务已经更新。之后我把 server 部署、桌面包发布和安装态验收拆开记录。

## 我把发布证据拆成四层

源码层回答实现能否编译和测试；打包层回答依赖和入口是否进入安装包；安装态回答真实 Electron 客户端能否登录、执行任务和恢复；生产层回答用户下载到的对象、别名、脚本和清单是否一致。前一层通过，不会自动替后一层背书。

| 证据层 | 我检查什么 | 结果能证明什么 |
| --- | --- | --- |
| 源码 | typecheck、test、build | 当前源码和构建产物可用 |
| 打包 | 四平台包、main/preload/renderer、依赖闭包 | 安装器内容与组合正确 |
| 安装态 | 真实账号、Workspace、文件、审批、重启 | 客户端实际行为可复现 |
| 生产 | server、COS、别名、安装脚本、latest | 下载和更新链路指向完整版本 |

## 每个发布脚本只负责一段链路

先在仓库根目录执行 package-release.sh，生成版本化产物。随后运行 verify-packaged-main-runtime，检查打包后的主进程能否加载实际运行时依赖。macOS、Windows、Linux 的安装器都要单独保留版本文件，不用一个平台通过推断其他平台。

安装态验收应在发布前完成：安装真实客户端，登录真实测试账号，创建本机 Workspace，做一次读写和审批，再重启恢复 Session、文件和 Artifact。源码测试和包体存在都不能替代这一步。

服务端部署入口是 deploy_xiaowei.sh，先核对目标服务和备份范围，再部署对应版本。不要把 dsh-ops 当成小薇生产入口。COS 对象上传后，检查版本文件内容、对象长度、CRC64-ECMA 和 Range 响应；Range 读取必须从实际字节范围验证，不用一段不完整流计算 SHA-256 代替。

## 我实际采用的发布顺序

1. 固定版本号和提交范围，完成源码检查与 package-release.sh。
2. 对生成的 macOS、Windows、Linux 包运行 verify-packaged-main-runtime，并检查每个平台安装器。
3. 在目标环境部署 server，使用 deploy_xiaowei.sh；确认运行的是 dsh-xiaowei.service。
4. 安装包进入测试设备，完成登录、Workspace、文件读写、审批和重启验收。
5. 上传版本文件到 COS 或 server，检查长度、CRC64-ECMA 和 Range。
6. 运行 publish-client-release.sh，先更新稳定别名，再更新安装脚本。
7. 最后写 latest.json，重新读取清单和安装入口，确认它们都指向已验证版本。

顺序中的“最后”很重要。latest.json 是更新器的发现入口，在前面的版本对象、别名和脚本没有稳定之前，不能先让它看到新版本。任何一步失败，都停在版本化文件阶段并保留旧版本。

## 页面、脚本和清单为什么会错位

遇到反馈失败时，先检查 Host profile 和服务清单，再检查 local-runtime/storages/message_feedback.json 是否写入。/health 只能做健康探针，不能证明反馈持久化或完整工具组合。

核对脚本名称、目标主机、systemd 服务名和实际进程。dsh-ops.service 与 dsh-xiaowei.service 不属于同一条证据。服务端更新后还要从安装客户端和下载入口重新走一遍。

如果 latest.json 已经变更，而安装脚本或某个平台对象仍旧，用户会拿到不完整版本。回退时先恢复 latest.json 和稳定别名到上一版，再处理安装脚本；版本化对象保留，便于复盘和重新发布。

## 安装态通过后我才允许发布

每次发布都记录版本、提交、平台、包名、包体校验、server 服务、COS 对象、别名、安装脚本、测试账号、Workspace、Session 和实际结果。这样某一层失败时，可以直接回到对应文件或服务，而不是争论一句“这个版本到底发没发”。

只要真实客户端无法登录、Workspace 列表未就绪、文件读写或审批失败、重启后 Artifact 消失，发布就不应进入 latest.json。生产下载校验失败时，先停稳定别名和清单提升，保留旧客户端和版本化对象。

看到“构建成功”时，我会继续问包是否加载正确；看到“安装器存在”时，我会继续问真实账号能否完成任务；看到“对象可下载”时，我会继续问 CRC64、Range 和清单是否一致。这样排障路径会回到具体文件、服务和客户端，而不是停在状态文案。

先让一个平台的安装态主线稳定，再扩展四平台和更新入口。新能力经过源码、打包、安装态和生产四层后再写发布结论。产品可靠性不是增加一个按钮，而是让失败时仍能保留旧版本并准确回退。

保留版本化包、校验输出、服务日志、COS 对象信息、清单响应和安装态截图或记录。publish-client-release.sh 完成后再复读稳定别名和 latest.json。这样即使 0.3.40 一类问题再次出现，也能判断是服务组合、部署目标、包体运行时还是下载清单出了偏差。

四个平台的验收记录还应注明操作系统、安装器类型和客户端实际版本。macOS 的包能启动，不代表 Windows 或 Linux 的主进程依赖也完整；同一版本号下，不同平台的 COS 对象也可能有长度或权限差异。每个平台都要从下载入口重新取包，而不是直接使用构建目录里的副本。

如果发布中途发现错误，我会先冻结变更，保存当前清单和服务日志，再把稳定别名恢复到上一版。回退完成后，用上一版安装器重新登录和打开一个测试 Workspace，确认回退本身没有破坏用户数据。新版本对象可以保留，等问题定位后再重新走完整发布顺序。

发布记录还要区分“上传完成”和“用户可用”。COS 返回成功只说明对象写入，CRC64 和 Range 检查用于确认对象内容可读；安装脚本可访问只说明入口存在，真实客户端登录和重启才说明产品路径可用。每个平台都需要自己的结果，不能用 macOS 的观察替代 Windows 或 Linux。

这套顺序也给后续路线留下了余地：新功能先在版本化包中验证，再进入稳定别名和安装脚本，最后才让更新器发现。发现问题时可以回到上一版，而不是在一个已经公开的 latest.json 上继续叠加修补。
