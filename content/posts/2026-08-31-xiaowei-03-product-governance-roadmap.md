我在发布小薇时反复遇到一个判断问题：什么叫“已经好了”？源码测试通过，只能说明一层；安装包能打开，也不能说明生产下载地址正确。0.3.40 的服务缺失反馈、误用 `dsh-ops` 和过早更新 `latest.json`，让我把发布拆成四个证据层级。

小薇基于 DeepSeek Harness 开源底座完成产品化和交付。底座的插件与事件机制是起点，企业治理要另外负责账号、环境、安装包、验收和回滚。

## 背景：0.3.40 让我重新看发布证据
### 适用读者与前置条件

本文面向负责打包、安装、发布和生产排障的工程师。前置条件是能访问仓库、构建工具和发布清单；真实账号、安装包和测试文件应使用专门的验收数据，不能直接改生产账号。

### 事故作为观察证据

0.3.40 的观察是界面可打开但服务缺失；这只能说明某个版本路径出现过问题。它不能被写成普遍结论，排障时要回到具体包、Host、客户端和服务清单。

0.3.40 的反馈故障很有迷惑性：按钮能点，RPC 路由也存在，本机分区仍提示“反馈保存失败”。追到 Host 组合后才发现，设备运行时漏挂了 `message-feedback`，所以没有真正的本地持久化服务。之后我不再用一个 `/health` 或一次构建结果代表产品可用。

另一次部署先跑了 `scripts/deploy_dsh.sh`，目标是当时未运行的 `dsh-ops.service`；生产实际服务是 `dsh-xiaowei.service`，入口应为 `scripts/deploy_xiaowei.sh`。服务端部署和桌面安装包也必须分开核对。

## 目标与非目标：控制发布风险，不制造虚假指标
### 目标读者和交付物

目标是交付可安装、可启动、可恢复的版本，并让发布报告标明源码、打包、安装态和生产证据。交付物包括版本文件、安装包、稳定别名、安装脚本和 `latest.json`。

### 权限与非目标

发布账号只能写指定版本目录和清单，验收账号只使用测试数据。非目标是编造用户量、成功率或业务收益，也不把 `implemented` 当作已发布。

目标是每个发布结论都写出证据来源：源码、打包、安装态或生产。目标还包括失败即暂停，保留可回滚的版本化文件，不让不完整的清单影响用户升级。

非目标是编造用户量、成功率或业务收益。当前资料没有这类指标，我只记录命令、版本、路径和验收结果。`implemented` 与 `approved` 也不能互换使用。

## 方案设计：把四层证据放进发布顺序
### 四层状态表

| 层级 | 证明什么 | 典型动作 |
| --- | --- | --- |
| 源码 | 类型、测试和实现 | `pnpm run typecheck`、`pnpm run test` |
| 打包 | 组合和依赖闭包 | `pnpm run build`、检查安装器 |
| 安装态 | 真实客户端行为 | 登录、文件、重启、恢复 |
| 生产 | 下载与更新链路 | 版本文件、别名、脚本、清单 |

### 发布顺序

版本文件先发布，确认校验后更新稳定别名，再更新安装脚本，最后提升 `latest.json`。任何一步失败都停留在版本化文件，不让更新器看到未完成清单。

源码层运行 `pnpm run typecheck`、`pnpm run test`、`pnpm run build`。打包层检查 macOS、Windows、Linux 产物和 Host 依赖闭包。安装态层安装真实 Electron 客户端，用真实账号、Workspace、文件和重启验证。生产层核对服务器、COS、版本文件和别名。

版本化产物先上传，稳定别名在校验后更新，`latest.json` 最后提升。任何一层失败都停在当前层，不提前给更新器可见。

## 详细设计：指标、审批和可恢复路径
### 输入、输出和权限

输入是源码 commit、构建配置、版本号和目标平台。输出是 macOS、Windows、Linux 安装产物及其版本清单。构建权限、COS 写权限和生产别名写权限应分离，验收账号不承担发布写入。

### 验收 E2E 流程

1. 备份当前安装包和用户数据。
2. 运行源码检查与构建，保存日志。
3. 生成目标平台安装包，检查版本和文件类型。
4. 安装客户端，使用真实测试账号和测试 Workspace 执行任务。
5. 关闭并重启，确认 Session、请求、回复和产物恢复。
6. 发布版本文件，校验后更新稳定别名和安装脚本。
7. 最后写入 `latest.json`，再次读取并核对所有字段。

### 可记录指标

记录账号串读、未批准副作用、安装失败、产物缺失、断线恢复失败、清单错误和别名错误。它们用于质量门禁，不等同于对外业务指标。

验收记录应包含账号串读、owner 不匹配、未批准副作用、Session 恢复、产物生成、连接重连和下载清单错误。这些是质量字段，不是对外宣传的业务指标。

桌面端的 mux 和 host 订阅要分别观察。缺少 pong 会终止旧连接代次并重新订阅；只有短时间没有应用事件，不能直接判定 Workspace 损坏。Skill 安装、浏览器交互等动作则要检查批准、撤销和失败提示。

## QA 与上线验收：0.3.43 给出的顺序
### 源码和打包检查

在仓库根目录运行 `pnpm run typecheck`、`pnpm run test`、`pnpm run build`。检查 Electron main、preload、renderer 和 `local-runtime` 资源，确认目标平台文件类型正确。

### 安装态检查

0.3.43 验收前备份 `/Applications/小薇.app` 0.3.42 和完整用户数据。安装后验证旧数据选择、真实回复 `LOCAL_ACCOUNT_ISOLATION_043_OK`、账号隔离和重启恢复，再进行生产发布。

### 验证清单

- [ ] 版本号、平台和安装器类型正确。
- [ ] 测试账号能登录并创建 Workspace。
- [ ] 本机目录、云端副本和附件没有混用。
- [ ] 断线后 Session 能恢复。
- [ ] 版本文件、稳定别名、安装脚本、`latest.json` 顺序正确。
- [ ] 每条结论标注 implemented、approved 或 observed。

0.3.43 验收前备份了 `/Applications/小薇.app`，并保留完整用户数据目录。安装后验证无所有者旧数据的认领或拒绝路径，再创建 `xiaowei-account-isolation-acceptance.A3xCSr` Workspace，获得真实回复 `LOCAL_ACCOUNT_ISOLATION_043_OK`。

最终包替换后重启，Workspace、Session、请求和回复首次加载即出现。随后才检查 macOS arm64、macOS x64、Windows x64 和 Linux x64 产物，并把 `latest.json` 放到最后。源码、打包、安装态、生产四层各自有结论。

## 踩坑：把“有文件”当成“可发布”
### 故障排查表

| 症状 | 检查顺序 | 处理 |
| --- | --- | --- |
| 页面可开但服务缺失 | bundle、profile、服务清单 | 停止发布并修复组合 |
| 安装包启动但本机 Host 不可用 | 依赖闭包、Host API | 重新打包并做安装态探针 |
| 下载到旧版本 | 版本文件与稳定别名 | 核对对象和缓存后再提升清单 |
| 更新器字段错误 | `latest.json` 内容 | 回到版本文件阶段，勿覆盖旧清单 |

### 误用 dsh-ops

`dsh-ops.service` 是旧部署入口的目标，不是当前的小薇生产服务，也不能证明本机能力。排查服务缺失时要检查实际 bundle、Electron 安装包和 Host，而不是只确认运维命令成功。

### 0.3.40 和 0.3.43 的差别

0.3.40 服务缺失是 observed 的失败反馈；0.3.43 的账号隔离、真实模型回复和重启恢复是另一条安装态 observed 证据。两者都不能替代当前发布版本的完整检查。

第一个坑是只确认安装器存在，没有确认它里面的 Host 依赖。第二个坑是把服务端健康检查当作模型和工具证明。第三个坑是先更新 `latest.json`，再发现某个别名或 Range 字节不对，导致新客户端拿到不完整发布信息。

我还见过规格状态带来的误读。`docs/specs/xiaowei` 中 `implemented` 说明实现证据已经存在，`approved` 说明方案获批或等待后续验收。它们都不能代替一次已安装客户端检查。

## 认知迭代：验收是产品设计的一部分
### 最佳实践

先写验收动作，再写发布说明。每项能力至少说明输入、输出、权限、执行位置、失败处理和回滚方法。没有这些字段时，先留在开发或批准状态。

### 限制

本机仍需要账号推理和钱包；部分浏览器、Web 搜索和联邦规格为 `approved`；Skill 的跨设备复制和版本历史尚未形成已发布承诺。发布报告不能填补这些缺口。

### 状态语义

`implemented` 是实现证据，`approved` 是批准或待验收状态，`observed` 是某个版本和环境中的实际观察。三者要使用不同动词，避免让读者把局部结果扩大理解。

## 运维参考与回滚
### 配置记录

为每次发布记录版本号、平台、构建命令、产物路径、校验结果、安装态账号、Workspace、Session、清单地址和操作者。COS 或生产服务器凭据不写入博客和日志正文。

### 回滚动作

若安装态失败，保留旧应用和用户数据，停止更新别名提升。若稳定别名已更新但 `latest.json` 未更新，先恢复别名，再核对版本文件；不要删除用户本机历史来“修复”发布。

### 路线判断

先补齐现有本机和云端路径的安装态探针，再考虑更多外部系统。浏览器授权、联网搜索和企业协作进入发布流程前，必须有对应规格、审批、撤销、失败和生产证据。

我现在把“能否验收”放在功能排期前面。一个工具若无法说明输入、权限、执行位置、结果和失败恢复，就不该只靠宣传语上线。发布报告也要让读者知道哪些是已验证事实，哪些是后续计划。

**能力状态提示。** 账号隔离、认证闸门、本机文档分析、连接连续性和本地 Skill 目录规格标为 `implemented`；本机 Workspace 环境、浏览器集成、账号 Web 搜索路由和联邦工具能力含 `approved` 规格。路线图是基于已知边界的判断，不代表已经排期或发布。

路线建议是先补齐安装态和生产探针，再考虑更多外部系统能力。新增能力必须同时给出撤销、失败和发布证据。

### 发布记录模板

每次发布记录版本、平台、构建命令、产物路径、校验结果、安装态账号、Workspace、Session、清单地址和操作者。测试凭据不写入文章或公共日志，异常时保留旧应用和用户数据。

### 最终检查顺序

先检查源码，再检查打包，再安装并执行真实任务，最后发布版本文件、稳定别名、安装脚本和 `latest.json`。若中途失败，停在当前层级并回滚可回滚对象，不用删除本机历史来掩盖问题。

### 变更后的复验

修改 bundle、Host 路由、安装脚本或清单字段后，至少重跑受影响的源码检查和安装态路径。只有重新获得对应证据，才可以把版本状态从观察结果推进到发布结论。生产清单的最后一步始终是 `latest.json`，不能提前暴露未完成版本。

### 官方命令入口

源码和包体准备阶段使用仓库提供的 `package-release.sh`。不带平台参数时生成 macOS arm64、macOS x64、Windows x64 和 Linux x64 四类产物；只验证单个平台时可传 `--mac`、`--mac:x64`、`--win` 或 `--linux`。

```sh
./apps/desktop/scripts/package-release.sh
./apps/desktop/scripts/package-release.sh --mac
```

脚本依次安装依赖、执行 TypeScript 检查、测试、renderer 构建和 Electron 打包。macOS 包生成后还要通过 packaged main runtime 检查，确认主进程能够从包内导入本机运行闭包。任何一步失败都停在打包层，不进入上传。

服务端部署先跑 dry-run，再使用 `deploy_xiaowei.sh`；不要用面向 `dsh-ops.service` 的旧入口替代它。该脚本面向 `dsh-xiaowei.service`，默认检查回环端口 18000 和 nginx 公网端口 18080，并在同步前创建远端备份。

```sh
./scripts/deploy_xiaowei.sh --dry-run
./scripts/deploy_xiaowei.sh
```

客户端发布先用 `publish-client-release.sh --dry-run` 检查四个平台文件、目标路径和 `latest.json` 内容，再执行正式发布。若明确只发布服务器且跳过 COS，可使用 `--skip-cos`；这不是完整双目标发布的验收结果。

```sh
./apps/desktop/scripts/publish-client-release.sh --dry-run
./apps/desktop/scripts/publish-client-release.sh
```

### server、COS 与校验

先把版本化文件写入 server 和腾讯云 COS，再检查 HTTP 状态、Range 字节和 CRC64-ECMA。Range 检查要读取文件开头、结尾和中间区间，确认响应长度与 `Content-Range` 一致。版本化对象通过后才更新稳定别名和安装脚本；`latest.json` 必须最后写入并重新读取。

### 回退顺序

安装态失败时保留上一版应用和用户数据，暂停稳定别名提升。若别名已变更，先恢复别名；若安装脚本已变更，恢复脚本引用；若 `latest.json` 已写入，先让它重新指向已验证版本，再重新读取。不要删除用户本机历史，也不要覆盖失败日志。

### 发布责任人

发布人要保留构建日志、安装态截图和清单读取结果。发现失败时，明确标注停在哪一层，并通知下一位处理人；不要用“已修复”替代可复现的命令和结果。

### 发布完成条件

完成发布的条件是：四平台版本文件可读取，server 与 COS 对象校验通过，CRC64-ECMA 和 Range 检查通过，稳定别名与安装脚本指向同一版本，最后的 `latest.json` 读取结果完整。任一条件缺失，都保持上一版可用。

### 版本保留

每次发布至少保留当前版本和上一份已验证版本的记录。生产排障先比较版本对象、别名和清单，再决定是否回退，不直接删除无法解释的对象。

### 记录完整性

构建日志、校验输出和安装态结果应与版本号对应保存。报告中把 `implemented`、`approved` 和 `observed` 分栏，避免后续维护者误读状态。

### 下一版入口

下一版发布从受影响文件和验收层级开始登记。先复现当前版本，再运行目标命令和安装态流程，最后更新发布对象；这样回退时仍能找到上一份已验证版本。

### 读者验收入口

维护者首次执行时，先在测试账号验证命令和安装包，再申请生产写权限。验证记录、版本对象和回退点齐全后，才进入正式发布。

发布结束后仍要读取一次最终清单，并从干净设备执行下载或安装探针。只有用户实际拿到目标版本，生产层证据才完整。

### 变更记录

发布报告还应记录哪些文件变更、哪些命令重新执行，以及哪个验收层级重新通过。没有新的安装态证据时，不将源码层的通过结果复制到生产结论中。
