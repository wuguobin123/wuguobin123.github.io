# 第一部分：踩坑清单（按症状索引）

## 一、部署类

| 症状 | 根因 | 解法 |
|------|------|------|
| `docker compose up` 后容器反复重启 | 配置文件挂载路径写错，容器内找不到 config | `docker logs <容器>` 看第一行报错，90% 是路径问题 |
| new-api 启动后页面空白 | 前端静态资源和后端版本不匹配 | 镜像 tag 不要混用 `latest` 和固定版本 |
| SQLite 数据库被锁 `database is locked` | 两个进程同时写 / 容器异常退出留下锁文件 | 停容器 → 删 `one-api.db-wal` 和 `one-api.db-shm` → 重启 |
| 容器时间差 8 小时 | 没挂载时区 | 加 `TZ=Asia/Shanghai` 环境变量 + 挂 `/etc/localtime` |

## 二、网络类

| 症状 | 根因 | 解法 |
|------|------|------|
| Cloudflare Tunnel 偶尔断连 | Quick Tunnel 模式本身不稳定（免费版无 SLA） | 换命名隧道（Named Tunnel）+ 自己的域名 |
| 流式响应卡顿、逐字蹦 | Nginx/CF 中间层开了响应缓冲 | `proxy_buffering off; proxy_cache off;` |
| 国内访问忽快忽慢 | 走了 CF 默认节点（美国） | CF 控制台开 Argo 或换香港/日本 VPS 落地 |
| 请求 504 但上游正常 | 中间层超时默认 60s，AI 长响应被掐断 | `proxy_read_timeout 600s` |

## 三、渠道类（掉坑最多）

| 症状 | 根因 | 解法 |
|------|------|------|
| **渠道测试通，实际调用 404** | new-api 某些 channel type 会改写请求路径（如 type=25 走 `/v1/responses` 而非 `/chat/completions`） | **把 base_url 临时改成 `http://127.0.0.1:9999`，用 nc/Python 起个监听抓真实请求路径**，这是我们排查 Kimi 渠道时用的大招 |
| 令牌验证失败 `invalid token` | new-api 查询时会**自动剥掉 `sk-` 前缀**，但 DB 里存的是带前缀的 | DB 里令牌 key 存**不带 `sk-` 前缀**的版本 |
| 令牌突然全部失效 | GORM 软删除：`deleted_at` 字段被意外置上时间戳 | `UPDATE tokens SET deleted_at = NULL WHERE deleted_at IS NOT NULL` |
| kiro-rs 账号被标记 disabled | 连续 3 次 401 就自动禁用，**且不会自动恢复** | 写探活脚本每 10 分钟自动重新 enable（见第 8 篇） |
| 换 type 值怎么调都是同样报错 | 报错其实是**渠道根本没被选中**（abilities 表没配模型映射），错误来自兜底逻辑 | 先查 `SELECT * FROM abilities WHERE model='k3'` 确认映射存在 |
| 渠道改配置不生效 | new-api 有渠道缓存（`channel_cache.go`） | 改完重启容器，或等缓存同步周期（默认几分钟） |

## 四、客户端类

| 症状 | 根因 | 解法 |
|------|------|------|
| Claude Code 连上但一直转圈 | Base URL 末尾多了 `/` 或少 `/v1` | 严格用 `https://your-domain/v1`，不多不少 |
| CC Switch 配置不生效 | 配置文件改完没重启客户端进程 | 完全退出进程再启动（不是关窗口） |
| 部分客户端报 SSL 错误 | 客户端系统证书库太旧，不认 CF 的证书链 | 换 Let's Encrypt 直接签发的证书，或更新系统 CA |
| 用量统计为 0 | 客户端走了非流式 + 某些渠道不返回 usage 字段 | new-api 设置里开"强制用量统计"（按 tokenizer 估算） |

## 五、运维类

| 症状 | 根因 | 解法 |
|------|------|------|
| 磁盘突然满了 | Docker 日志没做轮转 + new-api logs 表无限增长 | `docker compose` 加 `logging: max-size: 100m, max-file: 3`；定期清 `logs` 表 |
| 半夜服务全挂 | VPS 商家 OOM Killer 杀了容器（内存超了） | `docker stats` 看内存，2G 机器跑 4 个容器太挤，升到 4G |
| 备份恢复了但数据是旧的 | 备份的是容器层不是挂载卷 | 备份目标应该是 `/opt/ai-services/*/data` 这些**宿主机目录** |

> **排查三板斧**（90% 的问题用这三步定位）：
> 1. `docker logs <容器> --tail 100` 看应用报错
> 2. `sqlite3 one-api.db` 直接查表验证配置是否真的写进去了
> 3. base_url 指向本地端口抓包，看 new-api **实际发出去**的请求长什么样

# 第二部分：倍率与计费（源码级拆解）

new-api 的计费对新手是黑盒，这一节直接基于源码（`service/quota.go`、`common/constants.go`、`setting/ratio_setting/model_ratio.go`）讲清楚。

## 一、核心公式

一次请求扣的 quota 计算过程（`quota.go:60-86`）：

```
quota = (输入tokens × 1 + 输出tokens × 补全倍率) × 模型倍率 × 分组倍率
```

拆开看每个变量：

### 1. QuotaPerUnit（配额单位）—— 汇率

```go
// common/constants.go
var QuotaPerUnit = 500 * 1000.0  // = 500,000
```

**含义**：**1 美元 = 500,000 quota**。

- 用户余额显示 100 万 quota = $2
- 充值 $10 = 到账 500 万 quota
- 所以报表里 `总quota ÷ 500000 = 美元成本`

### 2. 模型倍率（ModelRatio）—— 模型贵不贵

定义：**相对于基准价 $2/1M tokens 的倍数**。

源码默认表（`model_ratio.go`）：

| 模型 | 倍率 | 对应官方价 |
|------|-----:|-----------|
| gpt-4.1-mini | 0.2 | $0.4/1M |
| gpt-4o | 1.25 | $2.5/1M |
| claude-3-haiku | 0.125 | $0.25/1M |
| claude-sonnet-4.5 | 1.5 | $3/1M |
| claude-opus-4.x | 2.5 | $5/1M |
| gpt-4-32k | 30 | $60/1M |

**规律**：`模型倍率 = 官方输入价($/1M) ÷ 2`。自定义模型（比如你的 k3）默认倍率是 37.5 左右（很贵），**一定要在控制台"模型倍率设置"里手动改成合理值**，否则用户调一次 k3 按天价扣费。

### 3. 补全倍率（CompletionRatio）—— 输出比输入贵

输出 token 通常比输入贵 3~5 倍，这个倍率单独算在输出 token 上：

- claude-sonnet：输出 $15/1M vs 输入 $3/1M → 补全倍率 = 5
- gpt-4o：输出 $10/1M vs 输入 $2.5/1M → 补全倍率 = 4

### 4. 分组倍率（GroupRatio）—— 你加的价

这是**中转站运营者自己的定价杠杆**（`quota.go:108-121`）：

| 分组 | 倍率 | 效果 |
|------|-----:|------|
| default | 1.0 | 按成本价 |
| vip | 0.8 | 8 折（优质用户） |
| intern | 0.5 | 半價（限制实习生高消费场景的实际配额消耗） |

注意还有个**用户组-渠道组交叉倍率**（`GetGroupGroupRatio`）：可以精细到"研发组走 Kiro 渠道时按 0.3 倍率扣（因为 Kiro 成本低），走 OpenAI 渠道时按 1.2 倍率扣"。

### 5. 缓存倍率（CacheRatio）—— prompt 缓存命中打折

命中 prompt 缓存的输入 token 按 `CacheRatio`（通常 0.1~0.5）计费，这就是为什么第 8 篇强调**粘性路由能省钱**——同账号连续会话缓存命中率高，实际扣费能降 50%+。

## 二、一个完整算例

用户（default 组，倍率 1.0）调用 claude-sonnet-4.5：

- 输入 2000 tokens（无缓存命中）
- 输出 800 tokens
- 模型倍率 1.5，补全倍率 5，分组倍率 1.0

```
quota = (2000 × 1 + 800 × 5) × 1.5 × 1.0
      = (2000 + 4000) × 1.5
      = 9000 quota

美元成本 = 9000 ÷ 500000 = $0.018
```

如果命中了 1500 tokens 缓存（CacheRatio=0.1）：

```
quota = (500 × 1 + 1500 × 0.1 + 800 × 5) × 1.5 × 1.0
      = (500 + 150 + 4000) × 1.5
      = 6975 quota  ← 省了 22%
```

## 三、给你的三个实操建议

1. **自定义模型必须设倍率**：k3、claude-via-kiro 这类自己接入的模型，按上游真实成本设置倍率（Kiro 成本≈订阅费摊销，可设 0.5~1.0）
2. **用分组倍率做成本转嫁**：Kiro 渠道分组设 0.3（订阅制边际成本近零），API 渠道分组设 1.0+（按实际付费），引导用户优先用低成本渠道
3. **对账公式**：`日报成本 = Σquota ÷ 500000`，每月和上游账单对一次，偏差 >10% 说明倍率配错了

# 第三部分：账号池低成本获取（合规路径）

> ⚠️ 先说红线：**所有账号必须本人/本团队真实注册使用**。买卖账号、接码平台批量注册、盗用他人凭证既违反各平台 ToS，也有实际法律风险（见第 7 篇）。下面只讲**合规前提下的成本优化**。

## 一、Kiro 账号（当前主力，成本最低）

Kiro 用的是 **AWS Builder ID** 登录，免费层就有可观额度。

| 路径 | 成本 | 额度 | 说明 |
|------|-----:|------|------|
| AWS Builder ID 免费注册 | $0 | 每月免费请求额度 | 一个邮箱一个号，Gmail 可用 `name+01@gmail.com` 别名语法，但**同主体多号有风控关联风险** |
| Kiro Pro 订阅 | $20/月/账号 | 额度大幅提升 | 团队成员自己的账号接入池，公司报销 |
| **推荐：团队自有账号入池** | 摊销 ~$0-20 | 视订阅 | 每个成员贡献自己的 Kiro 账号进池，本身就是额度共享 |

**实操**：50 人团队，让 15 个重度用户贡献自己的账号（他们本来就要用），池子就有 15 个号，边际成本为零。公司只需为没有账号的公共缓冲需求额外订阅 3~5 个 Pro 号。

**养号要点**：
- 新注册账号前 3 天低强度使用（每天几十次请求），突然高频易触发风控
- 每个账号固定从同一个出口 IP 调用（你的中转站天然满足——所有请求都从 VPS 出去）
- refresh token 定期巡检（第 6 篇的监控脚本），失效前自动刷新

## 二、Kimi（国内渠道，人民币结算便宜）

| 路径 | 成本 | 说明 |
|------|-----:|------|
| Kimi Code 套餐 | 按套餐档位，常有促销 | 国内开发票方便，团队走对公采购 |
| 按量 API | 按 token 计费，价格低于 OpenAI 同档 | 适合做降级兜底渠道 |
| 活动赠额 | $0 | 官方不定期送额度，关注官方公告 |

优势：**人民币结算 + 国内发票 + 无需跨境网络**，作为兜底渠道的综合成本比再开一个 OpenAI 号低。

## 三、OpenAI / Anthropic（最贵，只作兜底）

| 路径 | 成本 | 说明 |
|------|-----:|------|
| 官方 API 按量 | $$$ | 只放 priority 最低的兜底位，控制用量 |
| 团队版/企业版订阅 | 按席位 | 超过 20 人重度使用可考虑，比按量划算 |
| 新账号赠额 | $5 试用 | 聊胜于无，不要为此批量注册（违反 ToS） |

**原则**：按量 API 渠道只用来兜底，通过第 4 篇的优先级机制把它压到流量占比 <5%，月度成本可控在 $50~200。

## 四、其他低成本补充渠道

| 渠道 | 成本 | 适用场景 |
|------|-----:|---------|
| Google AI Studio (Gemini) | 免费层慷慨 | 非关键任务、摘要、翻译 |
| DeepSeek 官方 API | 极便宜（~$0.14/1M） | 代码补全等中低要求场景 |
| 阿里百炼/字节火山 | 国内便宜 + 新客赠额 | 国内企业合规要求场景 |
| Windsurf/Cursor 自有订阅 | 已购订阅的二次利用 | 团队已买的工具，通过 cursor2api 类项目接入（注意 ToS 边界） |

## 五、账号池成本总账（50 人团队示例）

| 项目 | 数量 | 月成本 |
|------|-----:|-------:|
| Kiro Pro（公共缓冲） | 5 个 | $100 |
| 团队成员自有 Kiro 账号 | 15 个 | $0（个人已有） |
| Kimi Code 套餐 | 1 个 | ~¥99 ≈ $14 |
| OpenAI API 兜底（<5% 流量） | 1 个 | ~$100 |
| VPS（2C4G 硅谷） | 1 台 | $15 |
| **合计** | | **~$229/月** |
| **人均** | 50 人 | **$4.6/人/月** |

对比：全员直接买 Claude Pro = 50 × $20 = **$1000/月**。自建中转站成本约为其 **23%**。

# 终篇小结

十篇走完，最核心的三句话：

1. **架构上**：瓶颈永远在账号不在服务器——2C4G + 账号池设计 > 高配机器
2. **计费上**：`quota = (输入 + 输出×补全倍率) × 模型倍率 × 分组倍率`，1 USD = 50 万 quota——自定义模型一定手动设倍率，分组倍率是成本调控的核心杠杆
3. **成本上**：合规前提下，团队自有账号入池 + 国内渠道兜底 + 按量 API 压到 <5%，人均成本能做到商业方案的 1/4
