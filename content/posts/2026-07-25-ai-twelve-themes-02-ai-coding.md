## 代码是 AI 第一个跑通的训练场

在所有 AI 应用场景里，Coding 第一个跑通完整闭环：模型写代码 → 编译/测试 → 错误回来 → 修 → 再跑。

这件事之所以重要，是因为它同时满足四个条件：

1. **可训练**：GitHub 上有海量公开代码
2. **可验证**：编译器、类型系统、测试、CI 都是廉价高密度的反馈信号
3. **可计价**：开发者愿意为生产力付费
4. **可迭代**：失败可以再来，成本可控

代码不只是「描述」，它是「可执行」的解决方案。所以 AI 从「会说」走向「会做」，Coding 是最自然的训练场。

## 六段演进

```
补全 → 对话 → AI IDE → Coding Agent → Repo Agent → 意图驱动软件生成
```

### 1. 补全：Copilot 阶段

下一个 token 预测，模型像个高级输入法。

代表：GitHub Copilot（2021）、Tabnine、Kite。

产品逻辑清晰、在编辑器里写几行代码就提升效率。但天花板也明显——只能补局部，不能改全文件。

### 2. 对话：聊着聊着写代码

模型能读整个文件，回答「这段代码什么意思」「帮我加个注释」。

代表：ChatGPT、Bard、文心一言早期。

带动了一波「我把代码贴进 ChatGPT 帮我看」的用法，但工作流是断的——代码得复制粘贴。

### 3. AI IDE：模型嵌入编辑器

模型直接进入 IDE，能读项目结构、调用 Terminal、跑 Git、看 Diff。

代表：Cursor、Cody、JetBrains AI、通义灵码。

这一步开始有「真工作流」了，开发者不再切换窗口。

### 4. Coding Agent：自主修改多文件

模型不仅回答，还能**自己规划任务、修改多个文件、跑测试、根据错误修复**。

代表：Devin、Claude Code、Codex CLI、Cursor Composer。

开始出现「SWE-bench 评测」—— 让 Agent 修 GitHub Issue 里的真实 bug，看能修多少。

### 5. Repo Agent：理解整个仓库

不只改一两个文件，而是理解：

- 仓库的整体架构和约定
- 跨模块依赖关系
- 团队的代码风格和 PR 习惯
- 历史 commit 和 review 评论

代表：Claude Code（带 claude.md）、Codex（带 AGENTS.md）、Cursor Background Agent。

这一步开始出现「项目级规则」文件：放进仓库根目录，Agent 每次执行先读它。

### 6. 意图驱动：从「怎么写」到「写什么」

用户说「给用户加一个导出 CSV 的功能」，Agent 自己拆解、自己实现、自己测试、自己开 PR。

这是产品经理级别的需求 → 软件交付。

代表：Aider Architect Mode、Devin、Codex Agent Mode。

目前还在早期，但方向明确。

## 为什么 Coding 能成为 ChatGPT 之后的下一个 PMF

我自己的判断是几条叠加：

### 反馈密度高

LLM-as-Judge 在很多场景不靠谱，但代码不同——能跑就是能跑，不能跑就是不能跑。这是天然的 ground truth。

### 已有工具链

Git、CI、Test、Lint、Type Check、Container、Docker——AI 不用从零搭建工程基础设施，工具链已经成熟。

### 单位经济跑得通

一个开发者月费 20-100 美元，AI 帮他省 5-10 小时，这就是清晰的 ROI。企业市场更明显，一个 100 人的工程团队一年能省下百万级别。

### 失败成本低

代码改坏了可以 revert，不像医疗和金融场景，错了就是错了。

## 竞争层次：模型不是唯一战场

很多人以为 AI Coding 竞争的关键是模型。这是 2023 年的看法，2025 年再看就不对了。

实际竞争层次是这样的：

```
┌────────────────────────────────────────┐
│  产品层：Diff 审核、团队协作、权限、计费   │
├────────────────────────────────────────┤
│  工程层：任务规划、错误恢复、状态管理     │
├────────────────────────────────────────┤
│  工具层：Terminal、Git、Test、Browser    │
├────────────────────────────────────────┤
│  上下文层：Repo Index、Memory、规则文件  │
├────────────────────────────────────────┤
│  模型层：推理、代码生成、长上下文         │
└────────────────────────────────────────┘
```

每一层都可能成为壁垒。**最贵的模型不必然产生最好的 Coding 产品。**

Cursor 早期没自有模型，靠 Claude + GPT 做出最受欢迎的产品之一。Claude Code 模型是 Anthropic 自家，但工程层（Repo Index、Memory、Agent Loop）才是护城河。

## 为什么「能写代码」≠「能交付软件」

这是 AI Coding 行业最大的认知陷阱。

写代码只是软件交付的一个环节：

```
需求 → 设计 → 写代码 → 测试 → CI → Code Review → 部署 → 监控 → 维护
```

一个 Coding Agent 写出 100 行没 bug 的代码，可能只完成了 30% 的工作。

剩下 70% 包括：

- 写单元测试（Agent 经常写完代码忘了写测试）
- 跑 CI 修复 lint/type 错误
- 开 PR 并写好 description
- 响应 reviewer 评论
- 等合并后部署
- 出问题后回滚

「Coding Agent 写出正确代码」和「帮团队交付功能」之间，是整整一截工程。

这也是为什么 Cursor / Codex / Claude Code 这些产品越做越像「项目管理工具」——它们在把所有环节接管起来。

## 关键认知

- 代码可验证，是 AI 第一个完整跑通的训练场。
- 竞争层次不止模型，工具链、上下文、工程层同样关键。
- 「能写代码」和「能交付软件」之间隔着测试、CI、Review、部署、监控。
- 项目级规则（AGENTS.md、claude.md）开始成为标配。
- 单位经济清晰，开发者付费意愿高。
- Coding Agent 不是替代开发者，而是放大开发者。

## 常见误区

- **把 Coding 当成「AI 编程大赛」**：实际上 90% 的工作是流程和协作
- **只看 SWE-bench 排名**：排名高不等于工程化好
- **让 Agent 直接动生产代码**：先 Worktree、后合并；先读后写
- **不给 Agent 项目规则**：每个仓库的约定不一样，泛化提示词效果差
- **把 AI Coding 工具当成 IDE 插件**：它本质是 Agent 工作台

## 评测指标：不是 Devin 排行榜

Devin 榜单上 13.86% 是一回事，工程实践是另一回事。

实际工程里该看：

- **任务完成率**：Agent 给你一遍就跑通的占比
- **Token 消耗**：完成一个任务花了多少 token、多少钱
- **人工介入率**：每个任务平均需要几次人工纠正
- **失败模式**：测试不通过、类型错误、依赖问题、忘记 commit
- **长任务能力**：能不能跑 30 分钟、跨多文件、跨多会话
- **跨仓库迁移**：换一个项目能否稳定工作

## 我自己观察到的几个反直觉的现象

1. **越长的代码越好写**：模型在 100-500 行规模的微调/重写上最强，反而是几行的小修补容易错（上下文不够）。
2. **Agent 自己装依赖比人还勤快**：npm、pip、cargo 出错时它会自己试不同版本。
3. **测试驱动反而帮 Agent**：先告诉它「需要哪些测试用例」，它写代码命中率高很多。
4. **Worktree 是工程师救星**：每个 Agent 任务开独立分支，错了直接扔，不影响主线。
5. **AGENTS.md 比 prompt 工程重要**：把项目约定、命名规则、避坑清单写进仓库根目录，Agent 表现稳定得多。

## 观察指标

- 任务完成率（含 1-shot、3-shot 修复）
- 单任务平均 Token / 成本
- 人工介入率与平均回合数
- 跨项目迁移稳定性
- 企业付费意愿与续费率
- PR 合并率（Agent 提出的 PR 实际被合并的比例）
