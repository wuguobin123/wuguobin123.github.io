0.3.43 之前，我遇到过一个不该靠运气发现的问题：换账号后，本机 Session 和历史可能还来自上一个账号。登录页显示新账号，并不能证明运行时根目录已经换了。这个事故让我把“当前用户”从界面上的一行字，落实到 authority、user、Host 和目录路径。

我还把数据分成三条路径：本机源目录、云端 Workspace 副本、附件。它们都能在任务里出现，却不能互相推断。这个问题最后没有靠一句“账号已切换”解决，而是落进了运行时目录、资源 owner 和一套可回退的认领流程。

## 0.3.43 之前，串账号风险藏在登录之后

我用两个测试账号、一个本机目录和几条 Session 做切换。问题不一定在登录页出现，常见表现是第二个账号打开后仍能看到旧历史，或者重启客户端后列表突然恢复成旧内容。只看账号名称和 Host 端口都不够。

早期运行时目录没有可靠 owner 时，系统无法安全猜测它属于谁。自动把目录挂给当前登录账号会把“最后一次使用者”当成所有者，拒绝使用又可能丢掉用户想保留的历史。正确处理需要一个持久的选择：拒绝，或明确认领。

## 我把目录、副本和附件拆成三条路径

本机 Workspace 指向用户选择的规范路径，是实时源。小薇不会因为创建 Workspace 就枚举和复制整个目录。文件变化留在本机，Session 只引用任务需要的内容。

执行 workspace.importDirectory 后，云端得到账号私有副本；本机后续修改不会自动同步。附件是独立的有界上传对象：本机附件留在账号专属设备 DSH_HOME，云端附件留在云端存储。附件上传成功，不等于目录已经导入。

| 对象 | 建立方式 | 归属与位置 | 删除或切换时的判断 |
| --- | --- | --- | --- |
| 本机源目录 | 用户选择路径 | 本机文件系统 | 不替用户删除源文件 |
| 云端副本 | 明确导入目录 | 云端账号 | 与本机源分开处理 |
| 附件 | Session 上传 | 本机 DSH_HOME 或云端存储 | 按附件对象处理，不推断目录同步 |
| Session / Artifact | 在 Workspace 中创建 | 创建时的 Host | 随资源位置恢复和路由 |

## authority 和 user 必须进入运行时根目录

本机运行时身份由 authority 和 user 派生不透明目录。桌面端同时维护本机与云端 Host，列表请求聚合两边，账号方法走云端，资源请求按资源 ID 的位置回原 Host。这样切换账号不是让用户手工换环境，而是先结束旧账号本机运行时，再启动新身份对应的运行时。

账号切换时，我会取消旧账号请求，保存新凭证，广播认证状态，启动新运行时，并等待 workspace.list 返回新账号资源。端口监听只能说明进程存在，不能提前把 Workspace 页面当作就绪。

如果旧目录没有 owner，首次遇到时展示选择。拒绝使用后，系统创建干净账号目录，并持久化拒绝决定；以后不会反复询问，也不会偷偷导入。确认认领后，系统把旧目录复制到账号专属运行时，保留原目录作为来源，并写入 claim 标记。这个标记会阻止其他账号再次认领同一份旧数据。

## 我怎样验证拒绝和认领都不会串账号

1. 用账号 A 产生本机 Workspace、Session 和一份历史文件。
2. 退出后登录账号 B，触发旧目录选择。
3. 选择拒绝，确认新账号进入干净目录。
4. 重启客户端，再次检查选择不会反复出现，账号 B 看不到账号 A 的历史。
5. 回到账号 A，确认原目录和原 Session 仍可用。

1. 准备没有 owner 的旧运行时目录，先复制备份。
2. 登录目标账号，选择认领。
3. 检查复制后的 Workspace 和 Session 位于目标账号目录。
4. 检查旧源仍存在，目标账号能打开复制内容。
5. 换另一个账号再次尝试，确认 claim 标记阻止重复导入。

## 一个路径解释不了所有数据

本机 Workspace 的路径是实时源，云端副本是另一个对象。页面能看到名称，不表示两者内容一致。要确认云端副本，必须记录 workspace.importDirectory 返回的云端资源 ID，并在云端 Host 读取。

先查新账号的 authority、user 和派生根目录，再等 workspace.list。不要因为本机 Host 已监听就重试大量请求。列表为空可能是新账号确实没有资源，也可能是运行时尚未完成加载。

认领应当复制，不是移动。发现原源被删除时，先停止后续迁移并恢复备份；产品验收应明确检查“复制后原目录保留”。

## 数据隔离要做正向和反向检查

对 0.3.43，我会记录客户端版本、两个账号、旧目录路径、拒绝或认领选择、派生目录、Session 列表、重启结果和标记文件。这样回头看时，能知道隔离是在源码测试里成立，还是已经在真实客户端里走通过。

删除 Workspace、附件或旧源前，先确认对象 ID、账号、Host、是否有副本和是否需要保留审计记录。本机源目录不由 Workspace 删除动作代替管理；认领复制也不意味着可以立即删掉旧源。

每个资源都要回答四个问题：谁创建，在哪个 Host，存在哪里，切换后如何恢复。回答不了时就不能继续扩大权限。账号切换不是 UI 状态切换，而是运行时生命周期和目录归属的变化。

先用非敏感目录做拒绝和认领试验，确认重启后仍符合预期，再处理真实资料。云端导入和附件上传分开记录。下一篇将把这些验收经验放到四平台发布链路中。

记录版本、账号、authority、user、旧目录、目标目录、选择结果、claim 标记、Workspace ID、Session ID 和重启观察。任何迁移异常先保留源目录和错误原文，不用清理动作掩盖现场。相关依据包括 local-workspace-account-isolation 规格、桌面 README 和本机验收报告。

我不会把账号切换后的“看不到旧数据”直接当成成功。还要检查新账号是否能创建自己的 Workspace，原账号回去后是否仍能打开原 Session，以及两个账号是否都能重启恢复。只有正向和反向都验证，才能排除“两个账号都读不到”的假成功。

附件也要单独做删除和恢复检查。本机附件的生命周期跟账号专属设备运行时有关，云端附件跟云端对象有关。清理 Workspace、退出账号或删除 Session 时，先确认附件是否仍被 Artifact 引用，保留需要的审计信息，再执行清理。这里不把目录删除、Session 删除和附件删除当成同一个动作。

我还会把“拥有数据”和“能访问数据”分开记录。账号能列出 Workspace，不等于拥有其中每个附件；Session 能看到一条历史，也不等于当前用户可以把它导出。权限检查要落到具体资源和动作上，尤其是复制、下载、删除和认领。

在实际使用中，最稳妥的顺序是先用空目录测试拒绝路径，再用可恢复副本测试认领路径，最后才接入真实资料。每次切换账号都保留旧账号回切检查，不把一次干净列表误认为隔离已经完成。
